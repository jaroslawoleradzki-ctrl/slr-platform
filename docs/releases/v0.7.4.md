# SLR Platform v0.7.4 — Import Review Decisions and Workflow Consistency

**Release date:** 2026-10-27
**Base version:** v0.7.3
**Breaking changes:** None intended
**Production deployment:** Not performed as part of this release

## Summary

v0.7.4 makes warning-import handling an explicit, attributed reviewer decision
and removes the remaining disagreement between deduplication, screening,
workflow status, and PRISMA.

Reviewers can now accept a warning import non-destructively or reject it through
a confirmation-gated, preflighted, single-transaction workflow. Rejection keeps
every research-audit record — import history, source records, skip audit,
warnings, and removed-publication snapshots — and reports the removed source
records as `removed before screening — rejected import` in PRISMA identification.

Deduplication, screening, and PRISMA now consume one active-corpus readiness
projection, so an approved-but-unmerged duplicate group is reported as
`merge_required` instead of completed.

Every scientific decision remains human-owned. No automatic duplicate merge, no
automatic inclusion/exclusion, and no LLM or autonomous screening behavior was
added.

## 1. Explicit import warning decisions

- New endpoints under `/api/v1/projects/{project_id}/imports/{import_id}/review`:
  - `GET` returns the import identity, source, counts, persisted warnings, the
    available decisions, and rejection readiness blockers.
  - `POST` records an explicit `accept` or `reject` decision with reviewer
    identity and optional rationale.
- Acceptance is non-destructive: it records the decision and warning snapshot
  and changes only the effective display status (`Zaimportowano`). Publications,
  duplicate decisions, screening decisions, quality assessments, extraction
  records, synthesis records, and PRISMA stage populations are unchanged.
- Acceptance and rejection are terminal. A conflicting repeat decision returns a
  conflict rather than rewriting the recorded decision.
- The GUI exposes `Akceptuję` / `Odrzucam`, a rejection confirmation dialog, and
  an actionable blocker explanation.

## 2. Guarded, atomic import rejection

Rejection is refused unless all of the following hold:

- every affected canonical publication is owned solely by the selected import;
- no other import references an affected publication;
- no affected publication belongs to a persisted duplicate merge or supersession
  chain;
- no affected publication has a duplicate-review decision;
- no downstream research record exists — pre-screening decision or archive
  entry, corpus-finalization membership, screening decision, full-text
  availability, quality assessment, extraction, or synthesis.

Ownership, merge, duplicate-decision, and downstream checks are reported as
machine-readable blocker codes with counts. The rejection request must carry an
explicit confirmation flag, and the whole operation runs in one transaction:
any failure rolls back every publication deletion, derived-state change, and
decision write, leaving the import active and unchanged.

## 3. Rejected imports remain auditable

- The import-history row, source records, skip-audit rows, original warnings,
  reviewer identity, timestamp, affected publication identifiers, and removed
  publication snapshots are retained.
- Rejected imports leave the active import list, active corpus, screening,
  extraction, synthesis, and export populations.
- `GET /imports` hides rejected imports from active history by default;
  `include_rejected=true` exposes the audit view.
- Rejected imports cannot be restored automatically after commit. Recovery
  requires a separate human-approved reconciliation using the retained source
  records and removed-publication snapshots.

## 4. PRISMA accounting for rejected imports

- Rejected source records stay in PRISMA identification history.
- Their removal is reported in a distinct pre-screening removal category labelled
  `removed before screening — rejected import`, exposed on the API as
  `records_removed_rejected_import` and in the PRISMA flow export annotations.
- The identified, removed, canonical, screened, and included counts reconcile
  without double counting; rejected publications are physically removed from the
  active corpus and are not also counted as archived or legacy removals.
- `PrismaMetricsService` remains the single counting path.

## 5. Deduplication and screening consistency

- One duplicate-readiness projection is shared by deduplication, workflow status,
  screening readiness, and PRISMA.
- Candidate groups are built only from active canonical publications; superseded
  and pre-screening-removed records cannot produce phantom groups after a later
  import.
- A pending group blocks both deduplication completion and screening readiness.
- An approved group without a persisted merge is reported as `merge_required`
  and `unmerged_duplicates` instead of completed.
- A rejected group satisfies duplicate review without a merge, and its records
  stay separate active canonical publications.
- Screening distinguishes pending review from approved-unmerged work instead of
  reporting a generic metadata/canonical-input conflict.
- The UI presents deduplication status from the backend readiness projection and
  cannot show a completed stage while duplicate work still blocks screening.

## 6. Database migration

One additive migration:

```text
migrations/0038_import_review_decisions.sql
```

It creates `import_review_decisions` with the terminal decision, reviewer
attribution, import status and warning snapshot at decision time, affected
source/publication identifiers, removed-publication snapshots, deletion and
retention counts, PRISMA treatment, and a unique `(project_id, import_id)`
terminal decision. Two indexes support project and decision lookups.

- No existing migration was edited.
- No destructive statement (`DROP`, `DELETE`, `ALTER`) is present.
- `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` keep the migration
  idempotent; `schema_migrations` records it exactly once.
- Upgrade rehearsal from the v0.7.3 schema (0001–0037) to 0038 on a disposable
  database: `PRAGMA integrity_check` = `ok`, `PRAGMA foreign_key_check` = no rows.

## 8. Known limitations

- Provider-import rejection is out of scope; terminal accept/reject decisions
  apply to warning file imports.
- A committed rejection has no automatic restore; recovery is a separate
  human-approved reconciliation.
- Reviewer identity is a self-asserted workflow identifier because the platform
  has no authentication/account layer.
- Historical imports without publication-ownership evidence can be accepted but
  cannot be destructively rejected.
- Rejected records remain in PRISMA identification by design; they are removed
  before screening, not silently deleted from the record.
- The full browser workflow was exercised through automated UI and integration
  coverage, not against a production-like dataset.

## Compatibility and upgrade notes

- No API or export contract was intentionally removed. Import-history and
  source-record responses gain additive review-state and effective-status
  fields; duplicate and workflow responses gain additive readiness information.
- Existing projects remain readable. Applying 0038 adds one empty table and two
  indexes; no existing row is rewritten.
- Existing duplicate decisions, merges, screening decisions, quality
  assessments, extraction records, synthesis snapshots, and audit trails are
  preserved unchanged.
- Upgrade path: back up the SQLite database, deploy v0.7.4, let the owning
  repository apply 0038, then verify `PRAGMA integrity_check` and
  `PRAGMA foreign_key_check`.
- Rollback path: the application can be rolled back to v0.7.3 while 0038 remains
  in place, because the table is additive and unreferenced by v0.7.3 code. Any
  accept/reject decisions recorded after the upgrade remain in
  `import_review_decisions` as audit evidence; restoring the pre-upgrade
  database copy is the only way to remove them.
