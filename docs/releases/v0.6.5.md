# SLR Platform v0.6.5 — Fetch All Available Search Results

SLR Platform v0.6.5 adds provider-agnostic automatic retrieval of every
result page each selected search provider actually exposes through its API,
alongside the existing single-step cursor pagination.

## Added

- **"Pobierz wszystkie dostępne" (Fetch All Available Results)** on the Search
  Strategy screen, next to the unchanged "Pobierz kolejne wyniki" button.
- One fetch-all job paginates each selected provider independently and
  sequentially:
  - OpenAlex — opaque cursor pagination (`meta.next_cursor`),
  - Crossref — opaque cursor pagination (`message.next-cursor`),
  - Semantic Scholar — offset-based pagination surfaced as an integer cursor
    string.
- Per-provider stop conditions: end of results, missing/repeated cursor,
  empty page while more results were claimed, a technical retrieval cap
  (e.g. the Semantic Scholar relevance-search ~1000 record ceiling) or the
  service's own safety caps (`FETCH_ALL_MAX_PAGES_PER_PROVIDER`,
  `FETCH_ALL_MAX_RECORDS_PER_PROVIDER`, `FETCH_ALL_MAX_SECONDS`), so
  pagination can never loop forever.
- Rate limiting is respected by reusing the existing provider clients:
  strictly sequential pages, per-client pacing (Semantic Scholar 1 rps),
  tenacity retry/backoff and `Retry-After` handling for HTTP 429. No parallel
  fetching of pages from the same provider.
- Partial success semantics: one provider failing never discards results of
  the others; fetched records are kept and snapshotted incrementally.
- Background job endpoints:
  - `POST /projects/{id}/search-strategy/executions/fetch-all` — starts the
    job, returns `202` with a job id; only one job per project at a time
    (`409` otherwise),
  - `GET .../executions/fetch-all/{job_id}` — cheap in-memory progress read;
    intentionally independent of the slow extraction `/progress` endpoint
    (the `/progress` → 504 regression remains a separate task),
  - `POST .../executions/fetch-all/{job_id}/cancel` — cooperative
    cancellation between pages that preserves already-fetched records.
- Live progress UI: per-provider fetched counts, provider-reported totals
  marked approximate (`~`), limit-reached flags, terminal statuses and total/
  after-local-filter counters — without promising that the reported match
  count is fully retrievable ("Pobierz wszystkie dostępne", not "Pobierz
  wszystkie N").
- Shared local constraint semantics via
  `app/services/search_strategy_support.py`: fetch-all jobs apply exactly the
  same post-query constraints as synchronous executions, including the
  v0.6.4 unknown-language rule (`language=None` stays a candidate under
  filters such as `["en"]`).

## Known limitations

- Resumable per-provider cursors are not stored between requests, so a
  fetch-all job restarts pagination from page one. Records are de-duplicated
  by `(provider, source_id)` within the whole job (nothing is added or
  snapshotted twice), but records downloaded earlier in the same session may
  travel over the wire once more.
- Job state lives in the backend process memory (single-process deployment);
  restarting the backend discards running jobs. Durable run tracking remains
  Phase 6.8.5 follow-up work.

## Compatibility and scope

- The existing "Pobierz kolejne wyniki" cursor flow is unchanged.
- v0.6.2 query rendering, v0.6.3 field compatibility and v0.6.4
  unknown-language semantics remain untouched.
- Deduplication stage, screening, quality assessment, extraction, synthesis,
  exports/PRISMA are unchanged.
- No database schema change or migration is required.
- No AI/LLM functionality is added.
