WP3 resolves the fundamental architectural defect in the SLR Platform's PRISMA reporting: the previous conflation of historical provider retrievals, pre-screening corpus preparation removals, active canonical research publications, and formal screening exclusions.

Under the new accounting model, the platform cleanly segregates four distinct populations across API endpoints, data transfer objects, UI visualizations, SVG diagrams, PDF generation, and XLSX dataset workbooks:
1. **Identification / Retrieval History**: Preserves exact immutable counts of all records identified from database providers (`import_history`) and manual file uploads, surviving subsequent downstream physical record deletions.
2. **Corpus Preparation**: Explicitly accounts for retrieval artefacts, non-scholarly items, and scope outliers removed during Import Review (`pre_screening_archive` + legacy `pre_screening_status='removed'`). These records never enter formal screening.
3. **Active Project Corpus**: Authoritative canonical research corpus admitted into downstream Normalization and Deduplication (`project_publications` active state).
4. **Formal Screening**: Rigorously bounded to records actually evaluated at Title/Abstract and Full-Text screening stages (`screening_decisions`).

## 3. Four-Population Accounting Model

The new accounting model establishes a formal mathematical and domain contract:

```
+-------------------------------------------------------------------------+
| A. IDENTIFICATION / RETRIEVAL HISTORY                                   |
| Source: import_history (provider fetches + manual file uploads)          |
| Total Identified = Records Providers + Records Files                     |
+-------------------------------------------------------------------------+
                                     |
                                     v
+-------------------------------------------------------------------------+
| B. CORPUS PREPARATION (PRE-SCREENING) REMOVALS                          |
| Source: pre_screening_archive + legacy pre_screening_status='removed'    |
| (Retrieval artefacts, non-scholarly items, out-of-scope metadata)       |
+-------------------------------------------------------------------------+
                                     |
                                     v
+-------------------------------------------------------------------------+
| C. ACTIVE PROJECT CORPUS (Admitted to Normalization & Deduplication)     |
| Active Records Before Dedup = Total Identified - Pre-Screening Removals |
| Active Canonical Records = Active Records Before Dedup - Duplicates     |
+-------------------------------------------------------------------------+
                                     |
                                     v
+-------------------------------------------------------------------------+
| D. FORMAL SCREENING                                                     |
| Stage 1: Title & Abstract (Screened, Excluded, Advanced)                |
| Stage 2: Full-Text (Sought, Assessed, Excluded, Included in Synthesis)  |
+-------------------------------------------------------------------------+
```

### Mathematical Invariants
1. **Identification Conservation**: $\text{Total Identified} = \text{Records Providers} + \text{Records File Imports}$.
2. **Corpus Balance**: $\text{Records Before Dedup} = \max(0, \text{Total Identified} - \text{Pre-Screening Removals})$.
3. **Deduplication Balance**: $\text{Active Canonical Records} = \text{Records Before Dedup} - \text{Duplicates Merged}$.
4. **Screening Isolation**: $\text{Title/Abstract Screened} = \text{Title/Abstract Included} + \text{Title/Abstract Excluded}$. Removals during corpus preparation satisfy $\Delta(\text{Screened}) = 0$.

## 4. PRISMA 2020 Compliance vs. Application Semantics

To uphold methodological integrity while providing full transparency for systematic review audits:
- **Official PRISMA 2020 Boxes**:
  - `Identification`: Databases & Registers (`records_identified_providers`, `records_identified_imports`).
  - `Records Removed Before Screening`: Formatted cleanly with itemized duplicates removed and pre-screening removals (`Pre-screening removals (n = ...)`).
  - `Screening`: Records screened, records excluded, reports sought, reports assessed, reports excluded.
  - `Included`: Studies included in review (`studies_included_synthesis`).
- **Transparency Distinction**: Pre-screening / corpus preparation removals are clearly labeled as pre-screening removals within the official PRISMA 2020 "Records removed before screening" section, distinguishing retrieval artefacts from formal methodological screening exclusions.

## 5. Preservation of Retrieval History Across Physical Deletions

In systematic reviews, when retrieval artefacts (e.g., 3,952 Crossref records) are permanently purged from working tables to save database storage or optimize query performance, methodological guidelines mandate that historical retrieval provenance remains unchanged.

- **Authoritative Provenance Source**: Historical identification counts are derived solely from `import_history` and `pre_screening_archive`.
- **Physical Removal Resilience**: When `PreScreeningReviewService.archive_pre_screening_removal(..., physical_delete=True)` deletes the row from `project_publications`, the publication snapshot is durably preserved in `pre_screening_archive`.
- **Deterministic Reporting**: `PrismaMetricsService` queries `import_history` for identification totals and `pre_screening_archive` for archived removals, ensuring identical metrics before and after physical deletions.

## 6. Deduplication and Normalization Contracts (WP2 Reconciliation)

WP3 establishes strict boundaries and contracts with WP2 (Normalization + Deduplication Integration):

- **Active Corpus Input**: Normalization and Deduplication operate exclusively on the Active Project Corpus (`get_active_publications(project_id)`).
- **Candidate Duplicate Groups**: `DuplicateGroupBuilder` and `ProjectDuplicateService` construct candidate duplicate groups only from active publications, ignoring removed artefacts.
- **Reporting Contract**: `PrismaMetricsService` reads duplicate decisions and merge records (`SqliteDuplicateMergeRepository` and `DuplicateReviewDecisionRepository`) without recomputing deduplication logic itself.
- **Independence**: WP3 contains no hardcoded or competing duplicate resolution algorithms.
