# v0.6.9 WP3.1 — Balanced Crossref Planner Correction & Hardening Report

## Executive Summary

Following the independent integration review (`docs/reviews/V0.6.9_WP2_WP3_WP4_INTEGRATION_REVIEW.md`), this work package (WP3.1) addresses the two MAJOR findings identified in WP3:
1. **Correction of the Claimed Balancing Invariant (Option B Adopted):** The mathematical contract for the balanced candidate planner has been corrected. While the heuristic greedy selection algorithm optimizes for pair diversity and penalizes reuse, balanced repetition frequencies (e.g. max frequency difference $\le 1$) are not universally guaranteed. The $3 \times 3$ (product $\le 10,000$) and $3^9$ (product $> 10,000$ fallback) adversarial shapes exhibit repetition frequencies of `[3, 2, 1]` (difference = 2). The formal contract has been narrowed to what is rigorously guaranteed: representation of $\min(B, L_j)$ distinct alternatives per axis $j$, hard budget bound $\le 6$, non-empty zero duplicates, and full Cartesian product preservation when $N \le 6$.
2. **Durable Resume Hardening & Incompatible Plan Rejection:** Enforced the core invariant: **"An old Crossref cursor must NEVER be sent with a different physical query string."** Resumed jobs now pin and reuse the exact candidate queries persisted in `SearchRunCheckpoint.plan_metadata["candidate_queries"]` (Outcome A). If an in-flight cursor cannot be verified against the active plan or lacks a matching plan fingerprint, the provider explicitly raises `IncompatibleCrossrefPlanError` before issuing any HTTP request, safely transitioning the provider status to `failed` and marking the checkpoint non-resumable (Outcome B).
3. **Textual Query Deduplication vs. Coverage Metadata Alignment:** In `_select_balanced_positive_and_plan`, candidate tuple coverage is computed strictly over the deduplicated executable query strings, preventing discrepancy if distinct synonym combinations collapse to identical text.
4. **Plan Fingerprinting:** A deterministic 16-character SHA-256 fingerprint (`compute_plan_fingerprint`) is computed from the candidate query list, attached to `RenderedQuery.metadata`, and embedded in newly emitted `crossref-plan:` cursors.

All 2301 backend tests pass without regressions, along with 100% clean passes on `ruff`, `mypy app`, and `git diff --check`.

## 1. Balancing Counterexamples & Contract Clarification (Option B)

### 1.1 Mathematical Reproduction

The independent review identified that the claim of balanced repetition (maximum frequency difference $\le 1$) is refuted by counterexamples on both execution branches:

1. **$3 \times 3$ AND query (Candidate product $9 \le 10,000$):**
   - Combinations: 9. Bound: 6.
   - Selected tuples: `(0, 0), (1, 1), (2, 2), (0, 1), (1, 0), (0, 2)`.
   - Axis 0 frequencies: index 0 appears 3 times, index 1 appears 2 times, index 2 appears 1 time.
   - Frequency distribution: `[3, 2, 1]`, difference = 2.
2. **$3^9$ AND query (Candidate product $19,683 > 10,000$, fast coordinate fallback):**
   - Combinations: 19,683. Bound: 6.
   - Selected tuples: 6 distinct coordinate tuples across 9 axes.
   - While every axis achieves 100% alternative representation ($3/3$), the 9th axis has indices distributed with frequencies `[3, 2, 1]` (difference = 2).

### 1.2 Decision: Option B

Rather than introducing fragile edge-case patches or computationally expensive integer programming solvers that could degrade performance or introduce new edge cases, **Option B** was selected:
- Retain the proven deterministic greedy algorithm.
- Narrow the documented contract and tests to the invariants that are mathematically guaranteed:
  - **Bounded output:** Emits at most $B = 6$ physical queries.
  - **Zero duplicates:** All emitted queries are distinct strings.
  - **Full Cartesian product:** When total combinations $N \le B$, all $N$ combinations are emitted in lexicographic order with 100% axis coverage.
  - **Guaranteed alternative representation:** Every positive axis $j$ with $L_j$ alternatives represents at least $\min(B, L_j)$ distinct alternatives, eliminating single-axis dimensional collapse.
  - **Deterministic ordering:** Identical queries and versions produce identical ordered plans without randomness.

Unit tests `test_counterexample_3x3_option_b_contract` and `test_counterexample_3_to_9_option_b_contract` have been added to verify these guarantees and directly document the `[3, 2, 1]` frequency distribution.

## 2. Adversarial Shape Sweep & Benchmark Analysis

An exhaustive sweep of adversarial shapes was executed to confirm invariants across the state space:
- Tested configurations: $7 \times 6 \times 4$, $2 \times 2 \times 2$, $10 \times 2$, $2 \times 10$, $7 \times 7$, $3 \times 3 \times 3$, $2^5$, $6 \times 6 \times 6$, permutations of $7 \times 2 \times 2$, $1 \times 20 \times 3$, $20 \times 20 \times 20$, $7^5$, $2^{14}$, $3^9$, $6^6$.
- Invariant results:
  - Every shape satisfied $\text{len(queries)} \le 6$.
  - Every shape produced 0 duplicate physical queries ($\text{len(set)} = \text{len}$).
  - In all cases, every axis $j$ achieved representation count equal to $\min(6, L_j)$.
  - Runtime benchmark:
    - Exhaustive branch ($\le 10,000$ tuples): $0.57\text{ ms}$ for $7 \times 6 \times 4$; $58\text{ ms}$ for $6^5$.
    - Fallback branch ($> 10,000$ tuples): $\le 0.08\text{ ms}$ for $3^9$, $2^{14}$, and $6^6$.

## 3. Resume Invariant & Plan Compatibility Hardening

### 3.1 The Invariant
> **AN OLD CURSOR MUST NEVER BE SENT WITH A DIFFERENT PHYSICAL QUERY STRING.**

In multi-query candidate retrieval, a Crossref cursor is pagination state local to a specific physical free-text query. If the planner produces different queries or a different query order between versions or deployments, applying an in-flight cursor at index $i$ to a new query string at index $i$ would silently contaminate search results.

### 3.2 Implementation Architecture

1. **Deterministic Plan Fingerprint:**
   - `compute_plan_fingerprint(candidate_queries) -> str`: Computes a 16-character SHA-256 hex digest over the newline-delimited query strings.
   - Attached to `RenderedQuery.metadata["plan_fingerprint"]` and `planner_version = "v0.6.9-wp3"`.
2. **Cursor Payload Versioning:**
   - `CrossrefProvider._encode_candidate_cursor(query_index, physical_cursor, plan_fingerprint)` produces `"crossref-plan:" + base64([query_index, physical_cursor, plan_fingerprint])`.
   - `CrossrefProvider._decode_candidate_cursor_payload(cursor)` safely parses 2-element (legacy) or 3-element (versioned) payloads.
   - `CrossrefProvider._decode_candidate_cursor(cursor)` maintains backward compatibility by returning the expected 2-tuple `(query_index, physical_cursor)`.
3. **Outcome A (Pinned Query Reuse):**
   - In `FetchAllSearchService._run_single_provider`, when resuming from an `initial_checkpoint`:
     - If `initial_checkpoint.plan_metadata` contains `"candidate_queries"`, those exact queries are pinned into `search_run.rendered_query` and passed to `provider.search_with_raw(..., candidate_queries=pinned_candidate_queries)`.
     - `CrossrefProvider.search_with_raw` detects pinned queries (either via parameter or `" || "` in `search_run.rendered_query`) and executes the exact pinned queries, completely isolated from any code changes in the planner.
4. **Outcome B (Explicit Incompatible Plan Rejection):**
   - If an in-flight cursor (`query_index > 0` or `physical_cursor != "*"`) is supplied:
     - If a cursor fingerprint is present and differs from the active plan's fingerprint: raises `IncompatibleCrossrefPlanError`.
     - If a cursor has no fingerprint (legacy cursor) and the candidate plan is not pinned: raises `IncompatibleCrossrefPlanError`.
     - If a legacy physical cursor is passed against a multi-query plan: raises `IncompatibleCrossrefPlanError`.
   - Raised before any HTTP request is issued (`0` outbound calls).
   - Caught in `FetchAllSearchService._run_single_provider`, which sets `state.status = "failed"`, `state.resumable = False`, and saves the checkpoint as non-resumable.

## 4. Textual Query Deduplication vs. Coverage Metadata

In `app/rendering/crossref.py`:
- Previous implementation deduplicated strings at the end (`dict.fromkeys(selected_queries)`), after `axis_coverage` had already been calculated from the index tuples.
- The updated implementation maintains an ordered seen set of formatted query strings during tuple collection. `axis_coverage` is calculated strictly from the unique tuples whose formatted strings were kept.
- Unit test `test_textual_query_deduplication_aligns_with_axis_coverage` asserts that when terms render to identical strings (e.g. duplicate synonyms), the coverage metadata accurately reflects the deduplicated executable queries.
