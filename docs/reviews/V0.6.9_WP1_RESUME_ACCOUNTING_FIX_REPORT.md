## Confirmed root cause

`FetchAllProviderState.kept_count` increments for records retained after canonical validation and local execution constraints. Recall-first validation retains `INDETERMINATE` records, so `kept_count` can exceed `canonical_accepted_count` or remain positive when accepted is zero.

`FetchAllSearchService._save_checkpoint()` persisted fetched, accepted, rejected, indeterminate, deduplicated, raw, mapped, malformed, and cursor/plan state, but omitted `kept_count`. The in-memory `get_status()` branch used `kept_count`; the checkpoint reconstruction branch substituted `canonical_accepted_count` for provider `kept_count` and job `kept_total`. The Resume initializer made the same substitution. The resumable-job summary had no kept field, and the frontend used `canonical_accepted_count` when restoring or selecting a historical job.

The query index and physical cursor were durably preserved. The zero display was an accounting defect, not evidence that Crossref replayed completed queries.

## Reproduction before fix

Added a SQLite-backed regression that starts a Fetch All job, retains a canonical match and an indeterminate record, persists a partial checkpoint, constructs a new `FetchAllSearchService` with fresh repository instances over the same database, and reads the normal status path.

Before the production fix, `uv run --extra dev pytest -q tests/unit/services/test_fetch_all_search_resume.py::test_status_reconstructs_durable_kept_count_after_restart` **failed as expected**: live `kept_total=2`, reconstructed `kept_total=1`, at the `kept_total` assertion. The final parametrized test also covers the production-shaped case with `canonical_accepted_total=0` and `kept_total=1`.

## Implementation

- Persist cumulative `kept_count` in existing checkpoint `plan_metadata`; no schema migration.
- Read it for historical status, resumable-job summaries, and Resume state initialization.
- For finalized v0.6.8 checkpoints without this field, recover a nonzero retained count from durable publication snapshots when available. Otherwise retain the previous accepted-count fallback.
- Add `kept_count` to the resumable-job summary response. The frontend's historical-job restoration and selection use it for provider `kept_count` and job `kept_total`, with a fallback for responses from older servers.
- Keep `canonical_accepted_count` distinct from retained count. No changes to canonical validation, recall-first retention, Crossref retrieval, six-query planning, provider deduplication, OpenAlex, or Semantic Scholar.

## Durable accounting semantics

`fetched_total` counts unique mapped provider records admitted to canonical validation. `canonical_accepted_total` counts definite canonical matches. `canonical_indeterminate_total` counts uncertain records. `kept_total` counts records retained after validation **and** execution constraints, before cross-provider result merging. Checkpoint metadata now persists that cumulative `kept_count`; the status endpoint and resumable summary read the same value. The regression compares fetched, kept, accepted, rejected, indeterminate, deduplicated, pages, raw, and mapped counters before and after restart.

## Crossref six-query regression

The new integration test uses the real `CrossrefProvider` and `CrossrefClient` with `httpx.MockTransport`. It generates six deterministic physical queries, serves two cursor pages per query, and records every `(physical_query, cursor)` HTTP identity. After three requests, one query is complete and the next is in progress; the job saves a SQLite checkpoint. A new service instance resumes the exact historical job ID from query 2's page-2 cursor and finishes all six queries.

All 12 request identities are unique; no pre-Resume identity occurs after Resume. Final assertions cover completion, 11 deduplicated retained results, fetched/kept/accepted/indeterminate counters, one malformed record skipped, raw/mapped counts, 12 pages, and status reconstruction after another restart.

## Known limitations

- A v0.6.8 checkpoint with no `kept_count` and no finalized snapshots cannot reveal the exact earlier retained count. Its fallback remains `canonical_accepted_count` until the resumed execution saves a new checkpoint with `kept_count`.
- For older multi-provider jobs, snapshots reflect merged results and may undercount per-provider pre-merge kept records. New checkpoints store exact per-provider counts.
- The four full-suite Crossref expectation failures require separate test maintenance or triage before a release gate can be declared green.
