## Architecture investigation

Pipeline mapped before coding (diagnosis §4 confirmed in code):

- `CrossrefQueryRenderer` (`app/rendering/crossref.py`) builds the bounded (max 6) deterministic candidate plan; metadata carries `candidate_queries`.
- `CrossrefProvider.search_with_raw` (`app/providers/search/crossref.py`) executes the plan, tracks `(query_index, physical_cursor)`, maps works, and previously **dropped** same-DOI repeats within one call and discarded `score`.
- `CrossrefClient.search_works` returns the raw payload; item-level `score` is available but was never read.
- Mapping (`map_work`) keeps title/abstract/DOI/date/language; validator input is title+abstract.
- `validate_canonical_query` returns `CanonicalValidationResult(status, matched_terms, missing_fields)`; per-group evidence is obtainable by evaluating each top-level AND child with the existing `evaluate_expression` — no reimplementation needed.
- `FetchAllSearchService._run_single_provider` validates every mapped candidate, applies `matches_execution_constraints`, dedups by source id (repeats silently skipped), snapshots kept `Publication`s (full JSON incl. provenance — no migration needed for new optional fields), and checkpoints counters + `plan_metadata` after every page.
- `SearchResultSnapshot.create` requires a provenance entry matching (provider, source_id, run_id); extra entries are tolerated.
- `ResultMerger` dedups provenance by `(source, source_record_id, run_id)` — multi-path entries would have been collapsed here without a key extension.
- No API DTO or frontend change is required: this WP is backend observability; status/result contracts are untouched.

Chosen design (narrowest): extend `ProvenanceEntry` with optional retrieval-path fields (durable via existing snapshots, restored on Resume) + one pure domain module for validation/retention/replay persisted as JSON in checkpoint `plan_metadata` (same pattern WP1 used for `kept_count`; rejected candidates are never snapshotted, so checkpoints are their only durable home) + a service-level replay reconstructor.

Alternatives considered and rejected:

- New SQL table for diagnostics: parallel subsystem with migration and a second source of truth.
- Recomputing validation at export from snapshots: rejected records are not snapshotted and retention outcome is not recomputable.
- Putting classification/evidence on `ProvenanceEntry`: mixes retrieval facts with verdicts; enrichment entries would inherit unrelated fields.
- New HTTP export endpoint: service-level reconstruction suffices; a test-suitable fixture meets the WP2 bar.

## Provenance model

`ProvenanceEntry` gains five optional, backward-compatible fields (`physical_query`, `physical_query_index`, `result_rank`, `provider_score`, `physical_cursor`); `rendered_query` keeps the combined plan string. One entry is appended per retrieval event.

New pure module `app/domain/crossref_diagnostics.py` (frozen pydantic, no I/O):

- `RetentionOutcome`: `retained` / `rejected_canonical_validation` / `rejected_execution_constraints` — deliberately separate from canonical status so "MATCH but constrained out" stays visible.
- `CrossrefMetadataCompleteness`: title/abstract/DOI/language/year/date presence computed from the pre-enrichment publication (answers "did Crossref provide an abstract?", not "does the enriched record have one"); optional-field extension point for later indicators.
- `CanonicalGroupEvidence`: per positive concept-group `evaluate_expression` result (`group_index`, `group_query`, `status`, `matched_terms`, `missing_fields`) — validator reused, never reimplemented.
- `CrossrefRetrievalPath` + `CrossrefRecordDiagnostic` (source id, DOI, title, run id, paths, completeness, status, evidence, outcome; `with_retrieval_path` merges idempotently).
- `retrieval_entries_from` / `retrieval_paths_from` (enrichment entries excluded: they carry no `physical_query`), `merge_retrieval_entries` (shared by provider and FetchAll), `build_crossref_replay_dataset` / `sort_replay_rows`.

Provider (`app/providers/search/crossref.py`): captures score (finite numbers only), rank (item index in page), query string/index, and request cursor at map time; same-DOI repeats within one call now append a provenance entry instead of being dropped. Single-query behavior is byte-identical apart from the new populated fields.

`ResultMerger` provenance key extended with the retrieval-path fields (entries without them keep the historical key — merge behavior for existing providers unchanged), so multi-path entries survive cross-provider merging.

## Multiple retrieval path handling

"Which physical Crossref queries retrieved this publication?" is answered by the `provenance` entry list (one entry per retrieval event) and, in the replay dataset, by one row per (record, path). Merge dedup key is `(query_index, cursor, rank)` per record: exact re-delivery collapses, distinct events accumulate. FetchAll-level repeats across pages/calls fold into the surviving kept record and its diagnostic without touching any counter.

## Persistence and Resume behavior

- Kept records: retrieval paths persist inside snapshot `publication_document` JSON (no schema migration); Resume restores `kept_records` from snapshots, so paths survive restart by construction.
- All candidates (kept + rejected): `FetchAllProviderState.record_diagnostics` persisted to checkpoint `plan_metadata["record_diagnostics"]` on every checkpoint save (after each page, as with existing counters).
- Resume (`_run`): diagnostics restored from checkpoint in both the completed and resumable branches; transient lookup indexes rebuilt; post-resume duplicates merge into restored diagnostics and kept records. Corrupt diagnostic rows are skipped leniently — diagnostics are advisory and must never break Resume; counters/kept records restore independently.
- Single source of truth: diagnostics are write-once facts in the same checkpoint JSON as the counters; live status and reconstructed status read the same payload. No second store.
- New accessor `FetchAllSearchService.get_crossref_replay_dataset(job_id)` reconstructs rows from live state when the job is known, otherwise from durable checkpoints — fresh processes and completed historical jobs work identically.

## Replay dataset design

`build_crossref_replay_dataset(diagnostics, job_id, search_run_id)` emits one row per (record, path) with job/run ids, source id, DOI, title, query/index/cursor/rank/score, completeness, per-group evidence, canonical status, and retention outcome; path-less records yield one null-path row. Rows sort by `(source_record_id, query_index, cursor, rank)` — repeated builds are identical. Bounded by the existing fetch-all caps (≤5000 records/provider); no live bulk fetch; no AI/LLM.

## Known limitations

- `record_diagnostics` grows with candidate count (≤5000/provider cap) inside checkpoint JSON saved per page; acceptable for diagnostic infrastructure, worth revisiting if jobs scale further.
- Cross-provider DOI merge-away is visible only at the aggregate `deduplicated_count`; per-record outcome stays provider-local (`retained`).
- Diagnostics restore skips corrupt rows leniently by design (Resume robustness over strictness).
- Live-search (`SearchEngine`) path gains retrieval provenance on records but no persisted validation annotation — durability lives in the FetchAll pipeline, which is the replay source.
- Completeness reflects provider-supplied metadata pre-enrichment by design; group evidence reflects the validated (possibly enriched) record by design — documented in code.
