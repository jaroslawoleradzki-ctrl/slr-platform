## 4. Work Package 2 Audit: Crossref Retrieval Quality

### Implementation Details
- **Problem Diagnosis**:
  - Crossref API free-text search syntax (`?query=...`) uses disjunctive (OR) scoring instead of strict Boolean AND.
  - Queries for multi-concept terms (e.g. `Lean AND Energy`) return publications that mention only `Energy` or `Lean` in completely unrelated fields (e.g., medical clinical trials mentioning "lean body mass" and "radiotherapy beam energy").
  - Crucially, ~70% of Crossref records completely omit abstracts.
- **Evaluation Mechanism**:
  - `app/services/crossref_retrieval_quality.py`: Evaluates bibliographic metadata against query terms:
    - `MATCH`: Concept terms present in title or abstract.
    - `NON_MATCH`: Sufficient abstract/title text is present, but concepts are demonstrably absent or match medical noise exclusion signatures.
    - `INDETERMINATE`: Metadata is insufficient (e.g. title is brief and abstract is absent) to guarantee exclusion without risking false-negative recall drops.
- **Preservation of Recall-First Semantics**:
  - Evaluator does NOT discard `INDETERMINATE` records. They are retained in the imported corpus for human pre-screening or screening inspection.
  - No automated hard gate filters out records without abstracts.
- **Audit Findings**:
  - Correct architectural decision: precision is assisted via diagnostics and pre-screening visibility, but automated filtering does not harm systematic review recall.

## 7. WP1 ↔ WP4 Reconciliation & Architectural Resolution

### Architectural Analysis: Vulnerabilities in WP1 Standalone
When inspecting WP1 without WP4, two critical semantic vulnerabilities were identified:
1. **Corpus Mutation After Screening Starts**: In WP1 alone, `ScreeningInputService` dynamically computed the screening pool by querying `project_publications` where `pre_screening_status == 'retained'`. If an investigator executed a new search/import *after* screening had commenced, new publications would silently slip into the screening queue without formal admission or baseline provenance.
2. **Pre-Screening Removal of Screened Records**: In WP1 alone, `PreScreeningReviewService.remove_record()` did not check whether a record had already been reviewed in Title/Abstract or Full-Text screening. A user could remove a record *after* it received a formal exclusion or inclusion decision, causing severe PRISMA accounting anomalies.

### Reconciled Architecture Implemented
To resolve these gaps without inventing a competing model, the following unified architecture was implemented on the integration review branch:

1. **Database Schema (`migrations/0031_corpus_finalization.sql`)**:
   ```sql
   CREATE TABLE corpus_finalizations (
       finalization_id TEXT PRIMARY KEY,
       project_id TEXT NOT NULL,
       finalized_at TEXT NOT NULL,
       finalized_by TEXT NOT NULL,
       total_candidates INTEGER NOT NULL,
       admitted_count INTEGER NOT NULL,
       removed_prescreening_count INTEGER NOT NULL,
       duplicate_count INTEGER NOT NULL,
       notes TEXT
   );

   CREATE TABLE corpus_finalization_members (
       finalization_id TEXT NOT NULL,
       publication_id TEXT NOT NULL,
       canonical_doi TEXT,
       PRIMARY KEY (finalization_id, publication_id)
   );
   ```

2. **Domain Contract (`app/domain/corpus_finalization.py`)**:
   - `CorpusFinalization`: Immutable record of the finalization event.
   - `CorpusFinalizationMember`: Exact admitted publications.

3. **Repository (`app/repositories/corpus_finalization_repository.py`)**:
   - `SqliteCorpusFinalizationRepository` and `InMemoryCorpusFinalizationRepository` with `save_finalization`, `get_latest_finalization`, `is_finalized`, and `get_admitted_publication_ids`.

4. **Service (`app/services/corpus_finalization_service.py`)**:
   - Adapts WP1's `project_publications` and deduplication merge records.
   - Computes admitted count = candidates - pre-screening removed - deduplication duplicates.
   - **Idempotency Guard**: If project is already finalized, `finalize_corpus()` returns the existing finalization record without creating duplicate rows or altering membership.

5. **Screening Boundary Protection (`app/services/screening_input_service.py`)**:
   - In `get_active_publications`: Checks `corpus_finalization_repo.get_latest_finalization(project_id)`.
   - If finalized: **Only publications recorded in `corpus_finalization_members` are returned**. Post-finalization imports are completely invisible to formal screening.
   - If not finalized (legacy projects): Fallback to dynamic `pre_screening_status == 'retained'` maintains 100% backwards compatibility.

6. **Pre-Screening Mutation Protection (`app/services/pre_screening_review_service.py`)**:
   - In `remove_record()` and `restore_record()`:
     - Raises `CorpusFinalizedError` if project corpus has already been finalized.
     - Raises `RecordAlreadyScreenedError` if the publication has already received any formal screening decisions in `screening_decisions`.

## 11. PRISMA Invariant Verification

The PRISMA Statement requires that records identified through database searching and other sources are transparently accounted for across Identification, Screening, Eligibility, and Included phases.

### Invariant Checks
1. **Pre-Screening Removals $\ne$ Screening Exclusions**:
   - Pre-screening removal represents corpus preparation prior to the formal screening protocol.
   - Recorded strictly under PRISMA Identification phase metric `records_removed_prescreening`.
   - Never included in `records_screened` or `records_excluded_title_abstract`.
2. **Screening Denominator Protection**:
   $$\text{records\_admitted\_to\_screening} = \text{records\_identified} - \text{duplicates\_removed} - \text{records\_removed\_prescreening}$$
   $$\text{records\_screened} \le \text{records\_admitted\_to\_screening}$$
3. **No Retroactive Removal**:
   - Attempting to remove a record that has already been screened via `PreScreeningReviewService.remove_record()` raises `RecordAlreadyScreenedError`, preventing corrupting PRISMA screening denominator counts.
