## 1. Executive Verdict

**VERDICT**: REQUEST CHANGES

**BOOLEAN VERDICT**: NO

**MERGE READINESS**: NOT READY

**RECOMMENDED VERSION**: v0.6.7 (after fixes listed in §21)

### Rationale

The implementation demonstrates high architectural quality and solves the
original problem (uncontrolled Crossref explosion, lack of canonical
semantics). The canonical validator is well-designed, provider translations
are thoughtful, and audit infrastructure is solid. However, several issues
prevent an unqualified "canonical Boolean works correctly on all three
providers" statement:

1. **Mass INDETERMINATE from Crossref** (HIGH) — Crossref returns 0%
   abstracts in live testing; virtually all Crossref candidates become
   INDETERMINATE and are retained, defeating the purpose of canonical
   validation for precision.
2. **Semantic Scholar `is_lossless` misclassification** (MEDIUM) — the
   `_to_plain_text` normalizer strips punctuation (hyphens, parentheses)
   without generating a warning, causing `is_lossless=True` for queries
   whose physical form differs from the canonical form.
3. **Audit rows not cleaned on project deletion** (MEDIUM) — orphaned
   `search_run_audits` rows accumulate indefinitely.

None of these are crash-level blockers, but they compromise the SLR
reproducibility and precision guarantees that the platform promises.

## 6. Crossref Review

### 6.1 Query Planning

The Crossref renderer uses a **bounded positive-anchor strategy** instead of
a Cartesian product:

- For the canonical 3-block AND query, it selects the smallest OR block (LEAN
  with 5 terms)
- Generates 5 physical queries: `"Lean Management"`, `"Lean Manufacturing"`,
  `"Lean Production"`, `"Kaizen"`, `"Continuous Improvement"`
- Each is sent as a separate `query=` parameter to the Crossref API
- **NOT 245 queries** (5×7×7) — this is correct and well-documented

### 6.2 Recall Analysis

The positive-anchor approach is **sound for recall** because:

- For any paper matching `LEAN AND ENERGY AND CONTEXT`, it must match at
  least one LEAN term
- Querying all LEAN terms forms a candidate superset containing every
  possible match
- Local canonical validation then enforces the full 3-block AND

However, Crossref's `query=` is **free-text relevance search**, not Boolean
filtering. This means:

- Crossref returns papers ranked by relevance, not filtered by exact match
- The query `"Lean Manufacturing"` returns 581,812 results, most unrelated
- Early pages may not contain the most relevant results

### 6.3 Safety Limits

- Max physical requests per call: 10
- Max pages per provider (fetch-all): 200
- Max records per provider: 5,000
- Max wall-clock time: 900 seconds
- Consistent upper bound: ~2,000 HTTP requests

### 6.4 Pagination & Cursor

- Crossref uses deep cursor pagination via `cursor=` parameter
- Multi-query cursor encoding: `crossref-plan:` + base64([query_index, physical_cursor])
- Repeated cursor detection ✅
- Empty page detection ✅
- Source ID deduplication within session ✅

### 6.5 Mass INDETERMINATE Problem

**This is the most significant finding of this review.**

Live testing confirmed that Crossref returns **0% abstracts** in the first
20 results for `"Lean Manufacturing"`. The canonical validator requires
abstract content to evaluate the ENERGY and CONTEXT blocks (since title alone
often doesn't contain all three groups).

For a typical Crossref candidate record:
- Title: "Lean Manufacturing: A Review" → has LEAN, has CONTEXT
- Abstract: **missing** → cannot evaluate ENERGY block
- Result: **INDETERMINATE** → **retained**

Scenarios verified empirically:

| Scenario | Title content | Abstract | Validator result |
|----------|--------------|----------|-----------------|
| A | Lean+Energy+Mfg | Present | MATCH |
| B | Lean+Energy, no Context | Present | NON_MATCH |
| C | Lean+Mfg, no Energy | Present | NON_MATCH |
| D | Energy+Mfg, no Lean | Present | NON_MATCH |
| E | Lean only | Missing | **INDETERMINATE** |
| F | Lean+Energy+Mfg | Missing | MATCH |
| G | Unrelated | Missing | **INDETERMINATE** |
| G2 | Kaizen only | Missing | **INDETERMINATE** |

**Consequence**: With Crossref's near-universal abstract absence, the
expected distribution for candidates is:

- Tiny fraction: MATCH (title proves all 3 blocks)
- Large majority: **INDETERMINATE** (retained)
- Small fraction: NON_MATCH (title disproves a block)

This means Crossref's contribution will be dominated by INDETERMINATE
records, significantly inflating the screening workload without improving
precision. The system correctly *counts* and *warns* about this, but the
user experience impact is severe.

### 6.6 Durable Resume

Not implemented. Documented as a known limitation. Acceptable for v0.6.5/6.

### 6.7 Assessment

Crossref implementation is **technically correct** but the practical value is
limited by the provider's data quality. The architecture properly handles
this degradation (counts, warnings, partial status), but the user should be
warned before starting a Crossref fetch-all.

### 7.3 `_to_plain_text` Normalization

The function strips non-alphanumeric, non-space, non-mark characters:
- `"Energy-Efficiency"` → `"Energy Efficiency"` (hyphen stripped)
- `"Manufacturing (Advanced)"` → `"Manufacturing Advanced"` (parens stripped)
- `"micro-CHP"` → `"micro CHP"` (hyphen stripped)

This normalization is applied **per term**, not to the assembled Boolean
query, so it correctly avoids stripping Boolean operators.

### 7.4 `is_lossless` Bug (Finding S2-LOSS-1)

The lossless flag is computed as `not warnings`. Warnings are only generated
for non-ANY field scopes. The `_to_plain_text` normalization **does not**
generate warnings.

Therefore, a canonical query containing `"Energy-Efficiency"` will:
1. Render to `"Energy Efficiency"` (different string)
2. Be classified as `is_lossless=True` (incorrect)
3. Be shown to the user as a lossless translation (misleading)

Live-verified: S2 treats `"Energy-Efficiency"` (0 results) differently from
`"Energy Efficiency"` (265,310 results).

**For the reference canonical query**: This bug does NOT apply because none
of the 19 terms contain punctuation. The bug is **latent** — it will
trigger with any future hyphenated/punctuated search term.

### 7.5 Assessment

Semantic Scholar integration is the strongest of the three providers. Live
verification shows excellent recall and precision. The lossless bug is real
but latent for the current canonical query.

## 8. INDETERMINATE Analysis

### 8.1 Validator Logic

The canonical validator (`app/services/canonical_query_validator.py`) uses a
three-valued logic:

- **MATCH**: All fields present, expression evaluates to true
- **NON_MATCH**: All fields present, expression evaluates to false
- **INDETERMINATE**: A required field is missing, so we can't prove or
  disprove the expression

For AND: NON_MATCH > INDETERMINATE > MATCH (pessimistic)
For OR: MATCH > INDETERMINATE > NON_MATCH (optimistic)
For NOT: MATCH↔NON_MATCH, INDETERMINATE stays

### 8.2 Pipeline Behavior

INDETERMINATE records are:
- ✅ Counted separately (`canonical_indeterminate_count`)
- ✅ Retained (not rejected) — correct for recall protection
- ✅ A warning is appended to the provider state
- ⚠️ They proceed to `kept_records`, get snapshotted, and are importable
- ⚠️ They can reach Screening
- ✅ The reason is traceable (missing_fields tuple)

### 8.3 Severity Assessment

For **OpenAlex**: Moderate impact — OpenAlex provides reconstructed abstracts
for most records, so INDETERMINATE should be rare.

For **Crossref**: **SEVERE** — 0% abstract rate means virtually all
candidates become INDETERMINATE. With 5 physical queries and up to 5,000
records, the screening workload could be overwhelmed with unvalidatable
records.

For **Semantic Scholar**: Low impact — S2 bulk search returns abstracts for
most papers. The INDETERMINATE rate should be low.

### 8.4 Impact on SLR

| Metric | Effect |
|--------|--------|
| Recall | Protected (INDETERMINATE retained) |
| Precision | **Degraded** for Crossref — many false inclusions |
| Screening workload | **Significantly increased** by Crossref INDETERMINATE |
| Reproducibility | Maintained — counts and warnings are recorded |

### 9.1 Confirmed Bug: S2-LOSS-1

| Attribute | Value |
|-----------|-------|
| **Provider** | Semantic Scholar |
| **File** | `app/rendering/semantic_scholar.py` |
| **Function** | `SemanticScholarQueryRenderer.render()`, line 64 |

| **Expected `is_lossless`** | `False` (strings differ after normalization) |

punctuation), so the post-retrieval validation is consistent. The bug is
cosmetic/auditability rather than functional — but for SLR reproducibility,
showing "LOSSLESS" for a query that was actually modified is a
methodological concern.

- OpenAlex: `is_lossless=False` ✅ (correctly lossy due to full-text scope)
- Crossref: `is_lossless=False` ✅ (correctly lossy due to candidate-only retrieval)

## 10. Canonical Validator

### 10.1 Code Review: `app/services/canonical_query_validator.py`

- **AND logic**: Correct — NON_MATCH if any child is NON_MATCH, INDETERMINATE if any
  child is INDETERMINATE, MATCH only if all children MATCH ✅
- **OR logic**: Correct — MATCH if any child is MATCH, INDETERMINATE if any child is
  INDETERMINATE, NON_MATCH only if all children are NON_MATCH ✅
- **NOT logic**: Correct — inverts MATCH↔NON_MATCH, preserves INDETERMINATE ✅
- **Quoted phrases**: Correct — uses ordered, contiguous token matching ✅
- **Token boundaries**: `\w+` regex with `re.UNICODE` ✅
- **Unicode**: NFKC normalization + casefold ✅
- **Case folding**: Uses `casefold()` (proper for Unicode) ✅
- **Title**: Always available (required field) ✅
- **Abstract**: Missing → field listed in `missing_fields` → INDETERMINATE propagation ✅
- **Keywords**: Used only for explicit `SearchField.KEYWORDS` ✅
- **SearchField.ANY**: Title + Abstract only (not keywords) ✅
- **Empty fields**: `publication.abstract is None` handled correctly ✅

### 10.2 Phrase Matching False Positive Check

"Lean Management" matching against "Lean ... Management" (non-contiguous):

The validator tokenizes `"Lean ... Management"` to `('lean', 'management')`
and `"Lean Management"` to `('lean', 'management')`. The ellipsis is
stripped by `\w+`. So these WOULD match — but in practice, the ellipsis
would produce intermediate tokens: "Lean improvement Management" →
`('lean', 'improvement', 'management')` and the phrase check would fail
because `('lean', 'management')` is not a contiguous subsequence.

For purely punctuation-separated cases like "Lean—Management" or
"Lean/Management", these tokenize to `('lean', 'management')` and WOULD
match `"Lean Management"`. This is correct behavior — these are
typographic variants of the same phrase.

### 10.3 Assessment

The canonical validator is **well-implemented and correct**. The three-valued
logic is sound, phrase matching is robust, and Unicode handling is proper.

## 11. SearchField.ANY / Keywords

### 11.1 Current Behavior

`SearchField.ANY` evaluates against:
- ✅ Title
- ✅ Abstract
- ❌ Keywords (excluded)

Keywords are only used when the canonical query explicitly uses
`SearchField.KEYWORDS` (e.g., `keywords:"Lean"`).

### 11.2 Assessment

This is a **deliberate methodological decision**, not a bug. The
documentation in `SEARCH_PIPELINE.md` states:

> Canonical `ANY` terms use title and abstract. Explicit `keywords`, `author`,
> and `venue` scopes likewise require an explicit field in the canonical AST.

The rationale is defensible: author-supplied keywords are often noisy,
inconsistent across providers, and can inflate false positives. The decision
to exclude them from default `ANY` matching is a conservative choice that
prioritizes precision.

However, this decision should be **explicitly documented at the UI level**,
so SLR researchers understand that their canonical query's `ANY` terms will
NOT match keywords unless explicitly scoped.

**Classification**: Methodological decision requiring confirmation — not a bug.

### 13.2 Crossref Physical Query Recording

For Crossref, `physical_query` stores the concatenated candidate plan:
`"Lean Management" || "Lean Manufacturing" || "Lean Production" || "Kaizen" || "Continuous Improvement"`

This is the **rendering output**, not the individual HTTP requests. The
individual physical queries are in `metadata["candidate_queries"]` on the
`RenderedQuery` object, but this metadata is NOT persisted to the audit
table.

**Issue**: To fully reproduce a Crossref search, you need to know which
individual queries were sent and in what order. The audit records the plan
but not the execution details (which queries completed, how many pages each
consumed, etc.).

**Severity**: LOW — the candidate plan is deterministic from the canonical
query, so it can be reconstructed.

### 13.3 Assessment

The implementation now:

1. ✅ Uses bounded candidate plan (5 queries, not 1 massive query)

**Can the original explosion recur?** No — safety limits prevent runaway
pagination, and the bounded candidate plan prevents the Cartesian product.

**But**: The new problem is different. Instead of 2.5M uncontrolled
candidates, we now get controlled retrieval with proper counting, but
Crossref's near-total abstract absence means most candidates will be
INDETERMINATE (retained but not truly validated). The numbers are
controlled; the quality is limited by Crossref's data.
