## Production defect

The service default `FETCH_ALL_MAX_RECORDS_PER_PROVIDER` is 5,000. After a valid partial checkpoint at that threshold, Resume starts successfully but can stop before another provider call. The UI then renders the safety stop as a provider response failure.

## Pre-fix reproduction

The six-query Crossref HTTP transport test was first changed to use a five-record cap in both executions. Execution 1 saved `(candidate query 3, cursor "*")`; a fresh service made zero HTTP requests on Resume. The pre-fix test failed at `len(requests) == 12` because only six requests had occurred. Command: `uv run --extra dev pytest -q tests/unit/services/test_fetch_all_search_resume.py::test_crossref_real_six_query_plan_resumes_without_replaying_physical_requests`.

## Existing safety-limit semantics

`app/services/fetch_all_search.py` defines default caps of 200 provider page calls, 5,000 distinct mapped source records, and 900 seconds. The page and record checks previously compared restored cumulative per-provider counters directly with those caps. The time clock was already fresh for a new job. Crossref separately bounds physical requests inside each provider call. No WP2 classification policy was changed.

## Existing Resume semantics

Checkpoints restore `pages_fetched`, `fetched_count`, canonical counts, raw/mapped counts, kept count, diagnostics, retained snapshots, and provider cursor. Crossref's encoded cursor carries candidate query index and physical cursor. Pinned candidate queries and plan fingerprint in metadata protect plan identity; malformed in-flight plans fail before HTTP. Resume kept the correct position but its restored counters exhausted the old budget immediately. Prior to this change, `provider_errors` included controlled partial safety stops, leading to the Polish “provider did not respond” message.

## Root cause

The loop used `state.pages_fetched >= max_pages` and `state.fetched_count >= max_records`. Both `state` counters are logical cumulative values restored from the checkpoint. A resumed execution at either cap had no fresh allowance. Both page and record caps could block; the observed 5,000 case was the record cap.

## New execution-vs-logical-counter contract

The contract was recorded before implementation in `V0.7.0_WP3_SEMANTICS_CONTRACT.md`. `fetched_count` and public `retrieved_count` continue to mean distinct mapped provider source IDs admitted to canonical validation, not HTTP observations. `raw_count` and `mapped_count` count provider observations, including repeated DOIs. `kept_count` counts retained provider records; final corpus records are merged by canonical DOI. All public counts and `pages_fetched` accumulate across Resume. Each execution measures provider page calls and newly admitted source IDs from its own start values; the wall-clock allowance starts with the new job. A single page can cross the record threshold, and the next call is withheld.

## Backend implementation

The loop subtracts execution-start page and record counts when checking safety caps. A structured `stop_reason` distinguishes `safety_limit`, `provider_failure`, and `pagination_stalled`. Controlled safety stops are excluded from `provider_errors`; provider failures retain that channel. A zero-progress budget stop is persisted as nonresumable. Resume rejects a job with no resumable checkpoint. Already terminal nonresumable providers are skipped and their checkpoint state is carried into the new job so multi-provider, multi-Resume chains retain all providers.

## Checkpoint semantics

Each page persists the next cursor. Crossref's candidate query index, physical cursor, pinned candidate queries, planner version, and fingerprint remain in checkpoint metadata. The new stop reason is also persisted. Resume still validates unsafe legacy or malformed plans before provider HTTP requests. The checkpoint repository keys by search run ID, so Resume advances the checkpoint into the new job ID; an earlier execution ID is historical audit context, not an alternate fork point.

## Frontend/status implementation

The progress response carries `stop_reason`. A resumable safety stop displays: “Pobieranie zatrzymano po osiągnięciu limitu bezpieczeństwa. Możesz wznowić pobieranie od zapisanego miejsca.” The provider row names the session safety limit. Resume is shown only when a terminal provider row says it is resumable. A completed execution has no Resume button. A real provider failure still uses the existing failure message.

## Single-Resume regression

The real Crossref six-query transport test starts with a five-record cap, records the exact next `(query index, cursor)`, restarts with new repositories/service, checks the first resumed physical request, proves `fetched_total == 10 > 5`, and proves no physical request overlap.

## Multiple-Resume regression

The same test executes a second bounded Resume and reaches the final Crossref page. Its three executions request six, five, and one physical pages, respectively. All twelve `(physical query, cursor)` identities are unique. Final status is `complete`, logical fetched total is ten, and Resume is false. A separate multi-provider test proves a complete provider remains present and skipped through two Resume executions.

## Duplicate DOI behavior

DOI `10.1000/0-b` appears on three physical query paths, including the last execution. Raw/mapped observations increase, while `fetched_count`, `kept_count`, and the final corpus count it once. The test asserts ten distinct result source IDs and retrieval-path query indexes `{0, 1, 5}`.

## Provenance/replay

The duplicate's merged Crossref diagnostic retains all three query paths. The final replay dataset is identical when rebuilt from a fresh service using only the durable checkpoint.

## Legacy checkpoint compatibility

The focused Resume suite covers missing and malformed candidate queries, unpinned legacy cursors, out-of-bounds query indexes, fingerprint mismatch, and valid pinned legacy checkpoints. The existing pre-HTTP rejection tests pass. Old checkpoints without `stop_reason` still deserialize with a null reason and keep their existing status behavior.

## Known limitations

The record cap counts newly admitted distinct mapped source IDs, as the existing public fetched counter does. The page cap also bounds executions consisting entirely of duplicates. Legacy checkpoints do not carry a structured stop reason. Provider-side result caps can still end a provider path without proving full coverage; WP2 owns retrieval quality.
