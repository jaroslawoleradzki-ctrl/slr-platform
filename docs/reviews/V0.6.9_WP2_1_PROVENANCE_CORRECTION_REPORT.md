## Resume identity fix

Root cause: `_run_single_provider` rebuilt `seen_source_ids` from
`state.kept_records` only. Rejected and constraint-rejected candidates are
never kept, so their restored diagnostics (correctly reloaded from the
checkpoint) were invisible to duplicate detection. A repeated DOI after Resume
took the first-seen path: counters incremented, a second diagnostic appended
(orphaning the first, whose index entry was overwritten), and replay split one
candidate across two diagnostics.

Correction (5 lines in `app/services/fetch_all_search.py`): seed the seen set
from kept records **and** restored diagnostic IDs:

```python
seen_source_ids: set[str] = {publication_source_id(p) for p in state.kept_records}
seen_source_ids.update(diagnostic.source_record_id for diagnostic in state.record_diagnostics)
```

The existing duplicate branch then merges the new retrieval path into the
restored diagnostic (and into the kept record when present) with counters
untouched. No provenance path is discarded; retained-record Resume flow is
unchanged; checkpoints without `record_diagnostics` restore the old behavior
exactly.

## Crossref score overflow correction

`_read_crossref_score` now catches `OverflowError` from `float()` and returns
null; finite numbers still convert; NaN/inf/bool/string/missing remain null;
record retrieval continues. Ranking semantics unchanged (score is
observability-only). Tests: provider-level `10**400` + valid score in one page
(both records retrieved, null + 5.0), plus direct edge cases (`-10**400`,
`inf`, `nan`, bool, string, non-dict).

## Positive-group / NOT correction

`group_evidence_for` now excludes top-level NOT children from positive groups
(existing Boolean semantics: NOT is an exclusion, not a concept group) and
returns no groups for a pure NOT query; positive AND children and generic

strategy-built queries, which contain no NOT children). Tests: AND-with-NOT
(2 groups, no Beta leakage, MATCH statuses), pure NOT (empty), strategy-built
2-group plan (still 2 groups).

## Checkpoint scaling benchmark

`test_checkpoint_scaling_at_provider_cap`: 5000 synthetic three-group
diagnostics (1 path each, representative titles) into a real SQLite checkpoint
row. Measured on this machine:

- 5,000 RECORD SERIALIZED SIZE: **4,898,334 bytes (~4.67 MiB)** — consistent with the reviewer's ~4.44 MiB estimate.
- SERIALIZATION TIME (model_dump + JSON encode at cap): **0.122 s**.
- CHECKPOINT SAVE TIME (single full-payload SQLite save): **0.033 s**.
- ESTIMATED WRITE BEHAVIOR: per-page cost grows linearly with accumulated records (~150 ms serialization at cap); at 20 unique records/page ≈ 250 writes serialize ≈ 0.6 GiB cumulatively — O(records × pages), matching the reviewer's ~0.55 GiB estimate.
- CLASSIFICATION: **ACCEPTABLE FOR v0.6.9** — worst single-page overhead is sub-second and bounded by the provider cap; no operational danger demonstrated. The quadratic cumulative cost stays tracked TECH DEBT: move to incremental storage if caps grow or latency monitoring flags it. No migration introduced.
