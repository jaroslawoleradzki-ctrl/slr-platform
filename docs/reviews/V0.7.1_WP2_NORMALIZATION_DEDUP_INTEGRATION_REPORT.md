## 4. Root cause confirmed

As identified in `docs/plans/V0.7.1_CORPUS_PIPELINE_INTEGRITY_PLAN.md` §§3.1–3.2
and verified in code before changing it:

- `normalize_project()` read `repository.get_publications(project_id)` —
  unfiltered `SELECT ... WHERE project_id = ?` — normalizing all 5677 rows
  including `pre_screening_status='removed'` records, then persisted them via
  `replace_publications()` (full DELETE + reinsert), baking removed records
  into the normalized output and the execution counts.
- `ProjectDuplicateService._find_group()` / `get_candidate_duplicate_groups()`
  preferred `get_all_publications()` (alias of the same unfiltered read), so
  `DuplicateGroupBuilder` clustered all 5677 records, producing groups
  containing or composed of removed artefacts.
- The WP1 Active Corpus abstraction (`get_active_publications`,
  `get_active_publications_with_position`, `count_active_by_project`) existed
  but neither pipeline stage used it.

- Single contract reused everywhere: WP1 `get_active_publications`

- New `repository_provides_method()` guard in `active_publication_filter.py`:

- `CorpusDerivedStateService.rebuild()` (`corpus_derived_state_service.py`):

  rebuild operation for WP4 to invoke (implementation + tests only; never
  executed against production in WP2).

## 10. Rebuild/reconciliation semantics

Chosen mechanism: **selective reconciliation** (not blind reset), preserving
legitimate review/merge audit work:

1. Normalization state is rebuilt by re-running `normalize_project()` on the
   current Active Corpus; the execution summary row is overwritten with true
   active counts (import adds already invalidate stale executions via
   `delete_for_project`, unchanged).
2. `reconcile_with_active_corpus()` deterministically identifies tainted
   history by rebuilding candidate groups from the full population and
   deleting only merges/decisions whose group contains a removed
   (`pre_screening_status='removed'`, via the new
   `get_pre_screening_removed_record_ids` accessor, so superseded-then-removed
   records are also caught) or physically absent member. Merges/decisions fully
   inside the Active Corpus — including legitimate historical merges whose
   non-canonical members are superseded by design — are preserved.
3. The operation is idempotent (second run removes nothing; proven by test N)
   and never touches publication rows, screening decisions, or finalization
   records (proven by test O and §14).
4. Full-reset remains available via existing `delete_for_project` on the
   normalization/decision/merge repositories (as `ProjectDeletionService`
   uses); WP4 may use either path — the end-state invariant is identical.

Resulting invariant: after a complete rebuild,
`derived active state = function(Active Corpus)` with no removed publication.

## 11. Canonical-state handling

- Normalization persists via per-record `update_publication`, so canonical
  documents of removed/superseded rows are left byte-identical (proven by
  test C: removed docs equal before/after). They are unreachable through every
  active read path (`get_active_publications`, screening corpus, exports).
- Removed rows are therefore *excluded*, not deleted: no silent historical
  data loss. Physical removal of the 3952 legacy removed rows is deferred to
  the WP4 production reconciliation, exactly as planned.
- Pre-existing `test_normalization_and_metadata_update_preserve_supersession_and_active_input`
  passes unchanged: post-merge normalization keeps supersession flags and
  active count 1.

## 12. Duplicate-state handling

- Stale merges/decisions referencing removed records are deleted by
  `reconcile_with_active_corpus()` (deterministic, idempotent, reported).
- Two pre-existing tests in `test_canonical_duplicate_merge.py`
  (`..._superseded_noncanonical_member...`, `..._superseded_canonical...`)
  encoded the old population semantics: they expected a superseded record to
  re-enter candidacy with a fresh import so the merge guard could reject it.
  Under the WP2 invariant a superseded record is outside the Active Corpus and
  can never be a candidate member again, so both tests were updated to assert
  the new protection mechanism (no live group contains the superseded member;
  re-merge attempt raises `already merged`; supersession map and audit records
  unchanged). The `must all be active` / `canonical must be active` guards in
  `merge_group()` are retained as unreachable-but-harmless defense-in-depth.
- Integrity audit orphaned-decision check now exempts decisions attached to
  persisted historical merges (they intentionally vanish from live candidates
  after supersession); merge/supersession validation still runs against the
  full Working Collection so legitimate merged members are not flagged.

## 18. Known limitations

- `prisma_metrics_service.py` still reads the unfiltered population (see §19).
- Normalization per-record updates are not wrapped in a single transaction;
  the operation is idempotent so a partial failure is healed by rerun. A
  future change may thread a shared connection through `normalize_project`.
- `merge_group()` active-member guards are now unreachable via live flows
  (groups are active-only by construction) but retained as defense-in-depth.
- Legacy `pre_screening_status='removed'` rows still physically present keep
  stale normalized documents; they are excluded from every active path and
  their physical archival is WP4's job.
