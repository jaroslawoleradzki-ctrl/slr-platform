## Failure classification

### Failure 1

- test file and test name: `tests/unit/rendering/test_query_rendering_integration.py::test_search_engine_provider_specific_rendered_queries`
- original assertion: `assert crossref_search_run.rendered_query == "sustainability"`
- expected behavior (per the stale test): Crossref renders the canonical query
  `AND(OR("lean management", "lean manufacturing"), "sustainability")` as the
  single term `"sustainability"`.
- actual behavior: rendered query is
  `'"lean management" sustainability || "lean manufacturing" sustainability'`
  (deterministic AND-product: 2 OR alternatives x 1 required term = 2 physical
  queries joined with `" || "`).
- classification: STALE TEST
- evidence supporting the classification: `SearchEngine.execute` renders via
  `get_query_renderer("crossref")` → `CrossrefQueryRenderer`, whose contract in
  `app/rendering/crossref.py` joins candidate queries with `" || "`.
  `build_crossref_candidate_queries` applied to this exact expression returns
  the two observed queries. Accepted renderer tests (e.g. the complex boolean
  test asserting a 4-combo `" || "` rendering) lock this contract. WP1 diff
  (`git diff 600ede8..HEAD`) touches no Crossref rendering/provider file.
- exact change made: imported `build_crossref_candidate_queries`; the test now
  derives the expectation from the builder, asserts the exact two-query list,
  asserts the rendered string equals the `" || "`-joined plan, and asserts
  `is_lossless is False`. The OpenAlex/Semantic Scholar assertions and the
  `openalex != crossref` check are unchanged.

### Failure 2

## Current Crossref contract

Evidence from code and already-accepted tests (all predating WP1):

- `app/rendering/crossref.py`: `MAX_CROSSREF_CANDIDATE_QUERIES = 6`. For an AND
  node the plan combines one anchor from every positive child; OR is a union of
  positive alternatives; NOT is a local-validation concern. Above the bound,
  evenly spaced mixed-radix ranks give deterministic coverage, explicitly not a
  lossless superset. The rendered string joins candidate queries with `" || "`,
  and metadata records `candidate_queries`, `possible_candidate_combinations`,
  and `planned_candidate_combinations`.
- `app/providers/search/crossref.py`: executes each candidate query as physical
  HTTP requests with per-query cursor tracking (`crossref-plan:` opaque
  cursor); `total_count` is surfaced only for single-query plans, otherwise
  `None` because overlapping free-text totals cannot be summed.
- Accepted tests: `tests/unit/rendering/test_crossref_renderer.py` (multi-query
  `" || "` rendering, bounded 6-query sampling, full-product-when-it-fits),
  `tests/unit/services/test_search_canonical_regression.py` (6-query plan with
  245 possible combinations, `total_count is None`, fixed cross-index positive
  paths), and
  `test_crossref_real_six_query_plan_resumes_without_replaying_physical_requests`
  (six physical queries, 12 unique `(physical_query, cursor)` identities, no
  replay after Resume).
- History: `2921170 fix(search): broaden bounded Crossref combination coverage`
  and `5ab146e fix(search): improve Crossref candidate retrieval correctness`
  introduced the broadened plan; the four failing tests were never updated.
- WP1 isolation: `git diff 600ede8..HEAD` (at WP1 commit `aa78119`) shows no
  changes to `app/rendering/crossref.py`, `app/providers/search/crossref.py`,
  or `app/providers/crossref.py`.
