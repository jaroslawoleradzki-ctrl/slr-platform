# v0.6.9 WP2/WP3/WP4 Independent Integration Review

## Executive conclusion

The three branches have no textual overlap and their main responsibilities are compatible. They are **not yet ready to integrate**: WP2 loses duplicate identity for rejected records across a process Resume; WP3's documented balanced-repetition invariant is false and its changed plan can reinterpret old in-flight Crossref cursors; WP4's recall-first comparison omits execution constraints. An integrated WP2-to-WP4 adapter also needs to convert a path-level replay dataset into a candidate-level population. No branch was merged for this review.

Severity counts below distinguish code defects from the required cross-WP adapter. There are no proven release blockers under the specified BLOCKER definition, but the MAJOR findings require correction before v0.6.9 integration.

## Original Crossref problem

The complete WP1 diagnosis was read. Crossref's general free-text `query` ranks broad matches; it does not enforce the application's exact Boolean phrases and conjunction. The bounded six-query plan sampled only 6 of 168 Lean × Energy × Manufacturing combinations and selected only `Manufacturing` from four third-axis choices. Crossref abstracts were absent for 25 of 40 sampled returned records. The local validator correctly produces `MATCH`, `NON_MATCH`, or `INDETERMINATE`; missing abstracts make even zero-of-three evidence potentially `INDETERMINATE`, and recall-first Fetch All retains it subject to bibliographic constraints. The diagnosis called for WP2 provenance/replay, WP3 balanced planning, WP4 uncertainty measurement, then WP5 fielded-retrieval evaluation. Neither the reported 4,500-record run nor a labeled population is locally available.

## WP2 review

### Implementation verification

The actual diff adds optional retrieval fields to `ProvenanceEntry`, a pure diagnostic/replay domain module, provider capture, path-aware `ResultMerger` identity, and Fetch All checkpoint/replay handling. Tests are all in one new service file. Scope is broadly WP2; validator, planner, and canonical retention rules were not edited. Existing tests were not altered. The focused and adjacent provider/Resume suite passed **144 tests** independently.

### Provenance correctness

The provider attaches the exact physical query and zero-based query index, request cursor (`*` on first page), zero-based **page-local** raw item rank, finite Crossref score, source/provider identity, and normalized DOI. Enumerating raw items before malformed mapping preserves rank semantics. Booleans, strings, NaN, and infinity become null scores. An integer whose conversion to float overflows raises `OverflowError` from `_read_crossref_score` before the malformed-record catch; this is a minor robustness gap. The score and rank describe retrieval, not canonical relevance. `ResultMerger` keys path positions separately; old entries without path fields keep the historical identity.

### Multi-path behavior

The provider merges same-source DOI paths within one call; Fetch All merges paths for a repeated DOI across calls; `ResultMerger` retains separate path entries. The added tests establish this for **retained** records, including a restart. For rejected records across a process Resume, Fetch All reconstructs `seen_source_ids` from `kept_records` only, although rejected diagnostics are restored separately. Independent local reproduction: return the same nonmatching DOI from two physical queries, stop after the first query, then start a fresh Resume service. The final state reports `fetched_count=2`, `canonical_rejected_count=2`, and **two diagnostics** for one DOI; the replay has paths at indices 0 and 1, but each row derives from a different diagnostic. The uninterrupted version reports one fetched/rejected diagnostic with two paths. This changes counters and candidate cardinality by restart boundary. See `app/services/fetch_all_search.py` at the initialization of `seen_source_ids` and `diagnostic_index` and the later `if source_id in seen_source_ids` branch. Rebuild the seen set from kept records **and restored diagnostic IDs**, and test rejected and constrained duplicates after restart. This is MAJOR.

### Resume durability

New snapshots carry optional provenance; checkpoints carry all candidate diagnostics. New jobs survive process restart and completed-job reconstruction in the supplied tests. Old checkpoints lacking `record_diagnostics` restore with an empty list, so they remain readable, but they cannot retroactively supply rejected-record replay. Corrupt rows are skipped without failing Resume; this is a deliberate availability tradeoff. The provider's old physical cursor format is still accepted. Compatibility of **in-flight old plans after WP3** is a separate cross-WP problem below.

### Replay dataset

Rows sort deterministically by source ID, query index, cursor, and page-local rank and contain query/score, DOI, canonical status, group evidence, missing fields inside each group, metadata completeness, and retention outcome. This is enough for candidate-level WP4/WP5 analysis after an explicit adapter, but rows are **one per retrieval path**, not one per candidate. Real labeled relevance or source abstracts are not supplied; the dataset is a diagnostic replay, not a gold standard. `group_evidence_for` reuses `evaluate_expression`. For an AND query containing NOT, it labels every top-level child as a positive group, including NOT; this is a minor generality/documentation issue for future evidence counting.

### Performance/scaling

Classification: **TECH DEBT**, not a demonstrated release blocker. `_save_checkpoint` dumps the entire growing diagnostic list into `plan_metadata`; SQLite JSON-encodes and replaces the same checkpoint row after every provider page. A representative three-group synthetic diagnostic serialized to about **924 bytes**; 5,000 such records form **4.44 MiB** of diagnostic JSON. At 20 unique records/page, roughly 250 checkpoint writes serialize about **0.55 GiB cumulatively** (before strategy, longer queries/titles, duplicate paths, and SQLite write amplification). Model dump plus JSON encode at 5,000 records took about 45 ms in this local synthetic check; database I/O was not benchmarked. Complexity is O(records × pages), approximately quadratic for fixed page size. Bounded at the provider cap, this may be acceptable for v0.6.9 with observed workload, but a cap-scale checkpoint latency/size benchmark and monitoring are required before release; move to incremental storage if operational limits are exceeded.

### Findings

- **MAJOR:** Rejected or constrained DOI repeated after process Resume is counted and diagnosed twice (reproduction above).
- **MINOR:** Path score extraction can raise on a JSON integer too large for float conversion; a malformed score should become null without stopping retrieval.
- **MINOR:** Top-level NOT is counted as a “positive” evidence group; align terminology and evidence extraction with actual positive groups before generic WP4 use.

### Verdict

**PASS WITH CONDITIONS.** Fix restart deduplication and add its regression before integration; keep checkpoint scaling as tracked debt with a cap-scale gate.

## WP3 review

### Algorithm verification

The new renderer stratifies axes longer than six; for products at most six it emits Cartesian order. For larger candidate products at most 10,000 it greedily scores unseen alternatives, usage, and new axis pairs; above 10,000 it chooses least-used coordinates with deterministic single-coordinate duplicate repair. No randomness or unordered-set iteration controls selection. The output is bounded by six and deterministic for the same input and code version. The supplied 11 focused tests and 62 adjacent rendering/canonical/Resume tests passed independently. These tests mainly cover intended shapes; they do not establish the universal mathematical claims.

### Claimed invariants

The documented claim combines (1) per-axis represented alternatives = `min(6, Lj)` and (2) when `Lj < 6`, repetition counts differ by at most one. **The combined guarantee is false.** With a 3×3 AND plan, actual tuples are `(0,0), (1,1), (2,2), (0,1), (1,0), (0,2)`. Axis 0 frequencies are **3/2/1**, so maximum difference is **2**. The same failure occurs in the >10,000 fallback for nine 3-valued axes: the last axis has 3/2/1. The weights are a heuristic, not a proof of balanced repetition. The independent shape sweep found no axis-coverage or uniqueness counterexample among the tested shapes, but that is not a universal proof of coverage for every supported Boolean shape. Revise the invariant or algorithm and add direct frequency assertions, including both execution paths.

### Adversarial analysis

The independent script exercised 7×6×4, 2×2×2, 10×2, 2×10, 7×7, 3×3×3, five binary axes, 6×6×6, each permutation of 7×2×2, 1×20×3, 20×20×20, five 7-valued axes, 14 binary axes, nine ternary axes, and six 6-valued axes. It also swept all shapes with 2–4 axes of lengths 1–7 and constrained five/six-axis shapes of lengths 1–3. Tested outputs respected six, uniqueness, determinism by pure ordered operations, full Cartesian output when the product fit, and expected per-axis coverage. The first balance counterexample was 3×3. Coordinate fallback repaired duplicates in the tested many-axis cases but can itself distort repetition. Exact query strings are deduplicated at the end; logical tuple coverage metadata is computed before that textual deduplication, so unusual rendering collisions deserve a focused integration test if arbitrary canonical term strings are supported.

### 7x6x4 verification

The actual planner produced six distinct queries with axis coverage **Lean 6/7, Energy 6/6, Manufacturing 4/4**, matching the stated fix. It removes the diagnosed third-axis collapse. It cannot change Crossref free-text semantics or recover the omitted seventh Lean alternative within six queries.

### Large-space fallback

It avoids materializing products over 10,000 and selects per-axis least-used values. For a 3⁹ space, coverage was 3/3 on every axis and no duplicate physical queries occurred, but the final axis failed balanced repetition. The exhaustive branch is bounded by 10,000 candidate tuples and six passes with pair scoring O(K²) per tuple; large K can still be expensive. The fallback uses O(6 × K × at most 6) coordinate work plus duplicate checks. No measured runtime blocker was found.

### Resume compatibility

Output order is stable **within the new planner version**, but the report's assertion that existing durable Resume remains compatible is too strong. `CrossrefProvider._decode_candidate_cursor` restores only `(query_index, physical_cursor)` and recomputes the plan from current code. On the diagnosed strategy, old query index 1 meant `"Lean Manufacturing" "Energy Consumption" "Manufacturing"`; new index 1 means `"Lean Manufacturing" "Energy Consumption" "Production"`. An old page cursor for index 1 will be applied to a different physical query after deployment. Checkpoint metadata contains the old `candidate_queries` but the provider does not use or validate it on Resume. Pin the saved physical plan/version for existing jobs, reject incompatible Resume explicitly, or drain affected jobs before rollout. Test an actual pre-WP3 in-flight checkpoint across the change. This is MAJOR.

### Findings

- **MAJOR:** 3×3 and 3⁹ refute the reported balanced-repetition guarantee. Fix the implementation or narrow the guarantee and downstream metadata contract.
- **MAJOR:** Legacy in-flight cursors can resume against a changed query at the same index; add plan compatibility handling before deployment.

### Verdict

**PASS WITH CONDITIONS.** The diagnosed axis collapse is fixed, but the claimed invariant and cross-version Resume contract need correction.

## WP4 review

### Isolation from production

The diff adds only a new experimental service module, its test file, and a report. No production path imports `uncertainty_experiment`; retention, snapshots, screening, DTOs, and frontend were unchanged. Independently, 18 focused tests and 45 tests including Fetch All Resume passed. WP3 is functionally independent of this branch.

### Policy correctness

The module reuses the canonical validator and keeps `MATCH`, `NON_MATCH`, and `INDETERMINATE` separate from experimental tiers. It handles generic group counts in supplied two-, three-, and four-group tests; zero-of-N and missing abstract are measured. Every built-in scenario assigns `INDETERMINATE` to MAIN or UNCERTAINTY, never REJECTED. The live Fetch All equivalence test uses five records with no constraining filters. In general, `CURRENT_RECALL_FIRST` assigns every canonical MATCH/INDETERMINATE to MAIN, whereas Fetch All retains it only when `matches_execution_constraints` succeeds. WP2's constrained-out MATCH fixture is a direct counterexample to population equivalence. Feed the policy engine only eligible records, or represent execution-constraint rejection explicitly and test the filtered case. This is MAJOR for using the experiment to estimate actual screening population; production behavior is unchanged.

### Methodological safety

STRONG means N−1 groups evidenced, WEAK means an intermediate count, and NO_EVIDENCE means zero; these are transparent analytical labels, **not empirically validated relevance probabilities**. The report states that caveat, although downstream UI must preserve it. There is no labeled recall estimate and no production policy promotion. `candidate_from_evidence_dict` expects flat `candidate_id`, counts, missing fields, and group statuses. WP2 produces nested `canonical_group_evidence`, `metadata_completeness`, and `source_record_id`; its rows also repeat once per retrieval path. Passing a WP2 replay row directly raises a missing-key error, and naive row mapping double-counts multi-path records. An integration adapter must group by job/run/source ID, derive evidence from the nested group statuses, union missing fields, carry abstract absence and retention outcome, and assert one candidate per source before running the experiment. This is a required cross-WP integration task, not a textual conflict.

### Complexity assessment

The implementation is 357 lines of production experiment code (the report's “~430” is imprecise) plus 420 test lines. Frozen typed input/output models and per-candidate assignments account for much of it and are reasonable for an auditable experiment. `SEPARATE_ALL_UNCERTAIN` and `EVIDENCE_TIERED_UNCERTAIN` currently assign the same population, differing only in the already-available tier counts; this is duplication of scenario presentation, not a release defect. The module remains isolated and cheap relative to provider retrieval.

### Findings

- **MAJOR:** `CURRENT_RECALL_FIRST` is only equivalent to the **canonical** retention step, not full Fetch All retention with execution constraints. Correct or scope the claim before using results for screening-volume decisions.
- **NOTE:** Strong/weak labels and example rates are analytical conventions, not measured topical relevance.

### Verdict

**PASS WITH CONDITIONS.** The isolated experiment is safe to retain, but its population contract and real WP2 adapter must be established before integrated use.

## Cross-WP compatibility

WP2 records a physical query string/index supplied by the provider; WP3 changes the provider's deterministic plan. They can work together for **new** jobs because both call the same renderer, and WP2's provenance can audit the new plan. The old-checkpoint issue above prevents claiming transparent Resume compatibility. WP2 and WP4 use the same canonical status vocabulary and the same validator; their row shapes and cardinalities differ, so an explicit adapter is necessary. WP3 and WP4 have no production-code overlap or direct semantic dependency. Do not interpret WP3's axis coverage as canonical recall, nor WP4 tier names as observed relevance.

## Merge-conflict analysis

The three diffs change disjoint paths: WP2 changes provenance/domain, provider, merger, and Fetch All; WP3 changes renderer and renderer/canonical tests; WP4 adds a new module/test. No textual three-way conflict is expected against the inspected baseline. Semantic integration points are: renderer plan identity vs provider cursor; WP2 checkpoint diagnostics vs WP3 plan metadata; replay path rows vs WP4 candidate rows; and WP4 experimental MAIN vs Fetch All's constrained kept set. Preserve WP3 `candidate_queries` metadata when WP2 extends checkpoint metadata. Do not resolve any semantic issue by simply discarding old checkpoints or silently excluding `INDETERMINATE`.

## Recommended merge order

The least coupled sequence is **WP2 → WP4 → WP3**, after the MAJOR branch findings are corrected and reviewed. WP2 establishes the replay substrate; WP4 can then add/test the adapter while the physical plan remains unchanged; WP3 goes last because it changes production retrieval and requires a deliberate legacy-cursor transition. This is a recommendation only; no merge was performed.

1. **WP2:** Expected textual conflicts: none. Required resolution: restore rejected/constrained source IDs on Resume and add restart duplicate tests; retain legacy checkpoint readability. Immediately run WP2 diagnostics, Crossref provider/provenance, Fetch All, checkpoint/restart, and six-query no-replay tests. Gate with full backend pytest, Ruff, mypy, `git diff --check`.
2. **WP4:** Expected textual conflicts: none. Required resolution: scope or implement constraint-aware recall-first population and add a candidate-level adapter for WP2 path rows. Immediately run uncertainty tests plus the new replay-adapter/count tests and canonical regressions. Repeat the full gate.
3. **WP3:** Expected textual conflicts: none. Required resolution: correct/document balancing contract and implement old-plan cursor handling, using persisted `candidate_queries` or an explicit incompatibility response; preserve WP2 provenance and WP4 adapter behavior. Immediately run planner adversarial tests, balanced-plan→provenance tests, six-query Resume/no-replay, legacy-checkpoint transition, and the full gate.

If any MAJOR correction is deferred, the affected branch should remain unmerged unless an explicit integration decision accepts and documents that exact risk.

## Agent engineering observations

- **WP2:** Scope is focused on auditability and tests cover real provider and restart flows, but the fixtures only duplicate a retained DOI. Checkpoint JSON is a convenient extension with scaling debt. Reuse of the validator and path-aware merger is sound; the Resume identity gap weakens the correctness claim.
- **WP3:** The diagnosed case and a broad range of adversarial shapes work, and output is deterministic. The mathematical explanation overclaims balanced repetition; supplied tests assert coverage but not frequency, and old-cursor compatibility was inferred from determinism rather than tested across code versions. The scoring/fallback implementation is more complex than the six-query bound alone would suggest.
- **WP4:** Strong scope discipline: production retention is untouched, statuses are canonical, and scenarios never discard uncertain records. Tests check generic group counts and the isolated policy, but the live equivalence fixture omits constraints and the adapter fixture does not use a real WP2 row. Model complexity is defensible for auditable experimental output; scenario duplication is modest.

These are observations about the commits, not general model rankings.

## Release recommendation

Correct the five MAJOR findings, add the cross-WP tests, complete the integrated regression gate, and then reassess release readiness. The WP1 diagnosis's broad Crossref semantics and missing-abstract precision problem remain; these work packages improve observability/planning/measurement but do not establish retrieval precision or validate a new retention policy. No release or deployment is recommended at this stage.
