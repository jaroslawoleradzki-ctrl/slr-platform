# WP3 Fetch All and Resume contract

Written before the implementation change, against development `046e3e7`.

- A logical Fetch All operation keeps cumulative per-provider counters across executions. `fetched_count` and public `retrieved_count` count distinct mapped provider source IDs admitted to canonical validation, not raw HTTP observations. `raw_count` and `mapped_count` count page observations, including duplicates. `kept_count` counts retained provider records; final merged corpus records are deduplicated by canonical DOI. `pages_fetched` is cumulative for audit and progress.
- Each execution receives fresh per-provider page and record safety allowances and a fresh whole-execution wall-clock allowance. The page allowance counts provider `search_with_raw` calls. The record allowance counts newly admitted provider source IDs, preserving the existing public `fetched_count` meaning. A page may put the execution over its record allowance; the next call is withheld. All allowances are checked before a call.
- A resumable checkpoint stores the next provider cursor, plus Crossref's pinned candidate queries and plan fingerprint. A resumed execution reads that position exactly and does not replay an already completed physical query or cursor. Complete providers are skipped. A provider returning no next cursor is complete, regardless of cumulative safety counters.
- Safety exhaustion is a controlled partial result with a durable checkpoint and a structured reason. Provider failures retain their separate error channel. Resume is offered only for a terminal provider with a valid continuation position. A structurally stalled provider is terminal and not advertised as usefully resumable.
- Canonical DOI deduplication and Crossref retrieval-path provenance span the logical operation. Final result counters and replay data describe the logical operation, not only the latest execution.
