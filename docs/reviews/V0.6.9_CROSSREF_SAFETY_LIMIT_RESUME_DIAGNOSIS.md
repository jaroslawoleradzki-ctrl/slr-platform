# SLR Platform v0.6.9 — Crossref Safety-Limit + Resume Diagnosis

Diagnosis-only. No code modified, nothing committed, pushed, released,
deployed, or cleaned up.

Production question: after Crossref Fetch All stopped at 5000 records with
6 deterministic physical queries and a safety-limit partial status, a
manually triggered Resume succeeded at the API level (no HTTP 500, no
traceback, no `IncompatibleCrossrefPlanError`, publication data returned)
but ended partial again on the safety limit. Is Fetch All + Resume
functionally correct?

Short answer: the traversal/resume machinery is correct (exact cursor
continuation, no repeats, canonical DOI deduplication, correct counters —
all proven), but under the production configuration Resume after a
record-cap stop cannot advance past the cap. The checkpoint is
positionally exact; the counters carried inside it re-trigger the same
limit. The frontend label for this state is wrong.

## 1. Where is the 5000-record safety limit defined?

`app/services/fetch_all_search.py:124-139`:

- `_env_int("FETCH_ALL_MAX_RECORDS_PER_PROVIDER", 5000)` at line 138
  (`DEFAULT_MAX_RECORDS_PER_PROVIDER`).
- Siblings: `FETCH_ALL_MAX_PAGES_PER_PROVIDER` default 200 (line 137),
  `FETCH_ALL_MAX_SECONDS` default 900 (line 139).
- Wired into the service constructor at lines 280-309
  (`max_pages_per_provider`, `max_records_per_provider`, `max_seconds`);
  production runs the defaults (observed stop at exactly 5000 records).

## 2. What exactly does the limit apply to?

One provider inside one fetch-all job execution — i.e. per
`(job execution, provider)`, checked at the top of the pagination loop in
`_run_single_provider` (`app/services/fetch_all_search.py:965-982`):

```python
if (
    state.pages_fetched >= self._max_pages_per_provider
    or state.fetched_count >= self._max_records_per_provider
    or elapsed >= self._max_seconds
):
```

`state` is `FetchAllProviderState` (lines 195-227): the mutable progress
of a single provider in a single job run. It is NOT per physical
candidate query (the 6-query Crossref plan shares one `state`), NOT per
Resume session in the code's intent — but see §6/§9 for why it behaves
as a cumulative logical-operation cap in practice.

`fetched_count` counts unique, successfully mapped records admitted to
canonical validation (comment at lines 200-203, increment guarded by
`seen_source_ids` at lines 1042-1049). So 5000 = 5000 unique candidates,
not raw HTTP rows. Page granularity overshoots: the check runs between
pages, so a stop reports `fetched_count` slightly above the cap
(proven by `test_record_safety_cap_stops_pagination_without_infinite_loop`,
`tests/unit/services/test_fetch_all_search.py:322-341`: cap 10 →
`fetched_count == 12`).

## 3. Hard product limit or defensive per-execution limit?

Designed as a defensive per-execution guard ("Safety limits guarding
against runaway pagination", line 134-136; v0.6.5 release notes
`docs/releases/v0.6.5.md:20` call them "service's own safety caps").
But because Resume inherits the cumulative counters from the checkpoint
(`_run`, lines 785-814, restore `fetched_count`, `pages_fetched`,
canonical counters verbatim) and compares them against the same
per-service caps, the limit acts as a **de facto global product limit
per (provider, search run)** unless an operator raises the `FETCH_ALL_*`
environment variables and restarts/resumes. There is no per-session
reset and no documented "5000/provider is the product ceiling" statement;
conversely there is no documented "Resume lifts the cap" statement
either (`docs/releases/v0.6.9.md:19-56` scope Resume identity and plan
pinning only).

## 4. What checkpoint is persisted when the safety limit is reached?

Lines 977-981: `status="partial"`, `limit_reached=True`,
`message="Stopped by the fetch-all safety limit before the provider
reported its final page."`, `resumable=bool(cursor is not None)`, saved
via `_save_checkpoint(job, state, cursor, ...)` where `cursor` is the
next *unfetched* position (loop variable already advanced at
lines 1099-1100/1131-1134 after the last completed page).

`_save_checkpoint` (lines 681-737) persists: `cursor`, `pages_fetched`,
`fetched_count`, all canonical counters, `deduplicated_count`, `status`,
`resumable`, full `plan_metadata` (strategy JSON, pinned
`candidate_queries`/`plan_fingerprint`/`planner_version` passthrough,
`record_diagnostics`, `kept_count`, raw/mapped/skipped counts), warnings.
For `crossref-plan:` cursors it additionally decodes and stores
`current_query_index` / `current_physical_cursor` /
`cursor_plan_fingerprint` (lines 706-715).

## 5. Does that checkpoint contain enough information to continue exactly?

Yes — positionally. The cursor is the opaque `crossref-plan:` token
encoding `(query_index, physical_cursor, plan_fingerprint)`
(`app/providers/search/crossref.py:400-434`; consumed at lines 211-273).
On Resume the service pins `candidate_queries`/`plan_fingerprint`/
`planner_version` from checkpoint metadata (lines 863-907, 989-1021),
restores `cursor` verbatim (line 860), rebuilds `seen_source_ids` from
kept records AND restored diagnostics (lines 946-951) so repeated DOIs
are never double-counted, and continues issuing requests from the saved
(query, cursor) identity.

Proven by the scratch reproduction below (§6: raised-cap resume called
exactly `['c3', 'c4', 'c5']` — the saved cursor first, no repeats) and by
`test_crossref_real_six_query_plan_resumes_without_replaying_physical_requests`
(`tests/unit/services/test_fetch_all_search_resume.py:330-444`), which
asserts `resumed_requests[0] == (physical_queries[1], "query-1-page-2")`
and zero intersection between pre- and post-resume request sets
(line 420).

## 6. What does Resume after the safety limit actually do? (A–E)

**B** — it remains capped by the inherited cumulative counters; with
identical caps it performs zero new provider requests and ends partial
again. Not A (no progress past the cap), not C (no repeats), not D (no
plan restart — pinned plan is reused).

Proof — scratch reproduction `/tmp/safety_resume_proof.py` (real
`FetchAllSearchService` + SQLite checkpoint/snapshot repos, 5 pages × 2
records, record cap 3; executed, not assumed):

- Session 1: `status=partial resumable=True limit_reached=True`,
  `fetched=4 pages=2 calls=['*', 'c2']`, checkpoint `cursor=c3`.
- Session 2a (IDENTICAL caps = production config):
  `status=partial fetched=4 pages=2 calls=[]` — **zero provider calls**,
  immediate partial with the same safety message, while `results=4`
  (served from durable snapshots — this is the "Crossref returned
  publication data" observed in production).
- Session 2b (RAISED caps, resuming the same chain):
  `status=complete fetched=10 calls=['c3', 'c4', 'c5']`, all 10 records
  in order, no repeats.

Mechanism: `_run` restores `fetched_count=5000` (lines 796-804), then
`_run_single_provider`'s loop-top check (lines 972-976) is true on entry,
so it breaks before any `search_with_raw` call. Page-granularity nuance:
if the stop landed marginally *below* the cap, one further page could
overshoot past it; once `fetched_count >= max`, all later resumes are
zero-call no-ops.

## 7. Why does the UI offer "Resume" after a safety-limit stop?

Nothing discriminates by stop cause. Backend marks the safety-limit
checkpoint `resumable=True` whenever a next cursor exists (line 980), the
finalized job reports `has_more=True` (line 1308, `partial_any`), and the
checkpoint appears in `list_resumable_jobs`. Frontend shows "Wznów
pobieranie" whenever the job is not running, not fully complete, and any
provider (or job) flag is resumable
(`frontend/src/components/search/FetchAllProgressPanel.tsx:103-108`,
button at 152-164; historical jobs at 251-323). A safety-limit partial
therefore always offers Resume, even though Resume cannot advance under
unchanged caps.

## 8. Is Resume after a safety-limit stop intentionally supported?

Accepted, but not usefully. `start_resume_job` (lines 347-406) requires
only "at least one resumable checkpoint" (line 368) and valid strategy
metadata; there is no exclusion for `limit_reached` checkpoints, and the
resume routers (`app/api/routers/search_strategy.py:470-501`,
`527-559`) return 202 for it. So the 202 + `resumable: true` contract
holds — which is why production saw "Resume executed successfully at the
API level". But the resumed run re-hits the same cap (§6), so support is
acceptance without progress (unless caps were raised between sessions).

## 9. Can repeated Resume exhaust all Crossref pages?

Under the production configuration: **no**. The exact-position machinery
preserves every listed invariant — deterministic pinned query order (§5),
exact cursor continuation (S2b + six-query test), no repeated
query/cursor positions (request-set disjointness asserted at
`test_fetch_all_search_resume.py:420`), canonical DOI deduplication
(`seen_source_ids` seeding at lines 950-951; `_merge_crossref_duplicate_paths`
at 549-577 keeps counters untouched), correct fetched/kept counters
(S2b `fetched=10`, ordered results; six-query test asserts
`fetched_total == 11`, `skipped_malformed_count == 1` at lines 424-436).
What is NOT preserved across repeated same-cap resumes is *progress*:
each session inherits `fetched_count >= max` and stops at the loop-top
check. The blocker is exactly that: **cumulative counters restored from
the checkpoint are compared against unchanged per-service caps**
(lines 796-804 feeding lines 972-976).

## 10. Exact blocker

`app/services/fetch_all_search.py`: the `_run` resume path restores
`state.fetched_count` / `state.pages_fetched` from the checkpoint and
`_run_single_provider` enforces `self._max_*` against those cumulative
values with no "already accounted, continue paging" distinction. Fix
directions (not implemented here) belong to v0.7.0: e.g. scope the
record/page caps per execution while keeping the checkpoint cursor, or
stop advertising `resumable` for pure cap-stops under identical caps, or
declare 5000 a hard product ceiling in the contract. Operator escape
hatch today: raise `FETCH_ALL_MAX_RECORDS_PER_PROVIDER` (and/or pages)
and Resume — the S2b path completes exactly.

## 11. Why "Część providerów nie odpowiedziała: crossref"?

Two independent layers:

1. Backend `_finalize_job` (lines 1310-1320) puts *every* non-complete
   provider with a message — including safety-limit partials — into
   `result.provider_errors` with text
   `"Fetch-all stopped early (partial): Stopped by the fetch-all safety
   limit ..."`. The backend message itself is accurate.
2. Frontend `SearchResultsSection.tsx:278-298` renders that list under a
   hardcoded static string `Część providerów nie odpowiedziała:` plus
   provider names, for ANY `provider_errors` entry regardless of cause.
   The existing frontend test locks this in:
   `frontend/tests/SearchResultsSection.test.tsx:296-304` feeds a generic
   `{ provider: 'crossref', message: 'Timeout' }` error and expects the
   same banner — no cause-specific branch exists anywhere in
   `frontend/src`.

So a provider that responded fully (and still has more to give) is
labelled non-responsive because the banner keys off list non-emptiness,
not off error semantics. (The v0.6.5 module docstring at lines 39-44,
claiming no resumable cursors exist, is stale since durable resume
landed in v0.6.7/v0.6.8 and adds to the confusion, but is not causal.)

## 12. Classification of the finding

A **combination**, with an intact core:

- NOT a provider bug (Crossref responded; cursor protocol exact).
- NOT a Resume-semantics bug (cursor/plan pinning, dedup, counters all
  proven correct — S2b, six-query resume test, WP2.1 resume tests in
  `tests/unit/services/test_crossref_diagnostics_resume.py`, adversarial
  resume tests in `tests/unit/rendering/test_crossref_resume_adversarial.py:520-640`).
- Safety-limit design issue (primary): cumulative counters + identical
  caps turn Resume-after-cap into a no-progress loop while `resumable`
  stays true — the Fetch All contract advertises continuation it cannot
  deliver without operator intervention.
- Frontend message bug (secondary, definite): unconditional
  "did not respond" label for a responded provider.
- Fetch All contract issue (framing): `provider_errors` mixes "provider
  failed" with "stopped by our own guard", and the UI repeats the mix.

## 13. Existing-test gap (verified, not assumed)

Searched `tests/unit/services/test_fetch_all_search_resume.py`,
`test_fetch_all_search.py`, `test_crossref_diagnostics_resume.py`,
`test_search_audit_hardening.py` for `max_records` / `safety` /
`limit_reached`: **zero** tests stop via the record cap and then resume.
Every resume test stops via `max_pages_per_provider` and resumes with a
*raised* page cap (e.g. 1 → 10 at `test_fetch_all_search_resume.py:222-256`;
3 → 20 at lines 397-416; multi-step 1 → 2 → 10 at lines 943-992). The
adversarial Resume suites likewise never hold caps constant across the
record-limit boundary. The production scenario (record-cap stop → fresh
service → same caps → progress beyond 5000) is therefore **unproven by
the existing suite**; the S2a/S2b reproduction above closes that gap by
demonstration: S2a = zero calls / still partial; S2b = exact continuation
to complete.

## 14. Intended behavior vs production observation

| Aspect | Intended (code + tests) | Observed (production) | Match |
|---|---|---|---|
| Bounded plan, 6 deterministic physical queries | yes | yes | YES |
| Stop at 5000 with partial + safety message | yes | yes | YES |
| Durable resumable checkpoint with exact next cursor | yes | Resume 202, no plan error | YES |
| Resume continues from exact position | yes (proven S2b/tests) | no new pages; partial again on safety limit | DIVERGES — explained by identical caps + cumulative counters, not by cursor/plan defect |
| "Publication data returned" on resume | new pages expected | data present (durable snapshots re-served; S2a `results=4` with `calls=[]`) | CONSISTENT once snapshot re-serving is accounted for |

No HTTP 500, no traceback, no `IncompatibleCrossrefPlanError`, no data
loss, no duplicated or skipped positions were observed or are predicted
by the code. v0.6.9's release scope (bounded planner determinism, Resume
plan identity/pinning, provenance, safe incompatible-plan refusal) is
unaffected: every v0.6.9-claimed behavior held in production.

## Finding classification

- NON-BLOCKING DEFECT / v0.7.0 FOLLOW-UP

Rationale: the traversal and Resume-identity machinery introduced and
hardened through v0.6.9 is functionally correct and behaved correctly in
production (no regression, no data corruption, no failed requests). What
is defective — Resume-after-record-cap accepted yet unable to advance
under unchanged configuration, plus a semantically wrong frontend banner
— predates v0.6.9's scope (caps date to v0.6.5), has an operator
workaround (raise `FETCH_ALL_MAX_RECORDS_PER_PROVIDER` /
`FETCH_ALL_MAX_PAGES_PER_PROVIDER`, then Resume, per the proven S2b
path), and does not violate any v0.6.9 release criterion. Follow-ups for
v0.7.0: (a) decide whether record/page caps are per-execution or global
and implement/contract that; (b) do not advertise `resumable` (or say
why) when only an unchanged cap blocks progress; (c) split frontend
"safety-limit partial" presentation from "provider did not respond";
(d) add a regression test for record-cap stop → same-cap resume (expect
documented behavior) and raised-cap resume (expect exact continuation to
complete).
