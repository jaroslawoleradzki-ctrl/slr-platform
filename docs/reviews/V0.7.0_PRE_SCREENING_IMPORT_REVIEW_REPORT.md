## 1. Executive Summary

In SLR Platform v0.7.0, we implemented a **pre-screening imported-record review capability** in the "Screen & Imports" module. This allows researchers to inspect bibliographic records retrieved from live providers (such as Crossref, OpenAlex, Semantic Scholar) or manual file imports (RIS, BibTeX) **before** they are admitted to the formal Title/Abstract Screening stage.

### Primary Goals Achieved
1. **Quality Inspection Before Formal Screening**: Researchers can inspect retrieval quality and remove clearly irrelevant, erroneous, or non-academic artefacts before freezing the screening corpus.
2. **Strict PRISMA Semantics Preservation**:
   - Records removed at this pre-screening stage **never count as "records screened"**.
   - Pre-screening manual removals are strictly distinguished from formal screening exclusions.
   - Non-destructive persistence: Records are not hard-deleted; rather, their pre-screening state is updated to `removed` and accompanied by an immutable audit trail in `pre_screening_decisions`.
3. **Auditability & Provenance**: Every removal persists an auditable controlled reason (`clearly_outside_scope`, `retrieval_artefact`, `incomplete_record`, `other`), optional/required notes, user attribution, and UTC timestamps.
4. **Undo / Restore**: Full support for restoring previously removed records before the corpus proceeds through formal screening.
5. **Bounded Pagination for Large Result Sets**: Server-side pagination, search, and status filtering prevent client-side performance degradation on 5,000+ record retrievals.
6. **Backward Compatibility**: Fully compatible with existing historical imports without destructive data migrations.

## 2. Architecture Discovered

Prior to v0.7.0, bibliographic items ingested into `project_publications` entered the Working Collection immediately. Formal screening operated on `get_active_publications`, meaning any ingested record was considered part of the potential screening corpus unless marked as superseded by a duplicate merge.

### Lifecycle Boundary Discovered & Formalized
To avoid conflating pre-screening corpus preparation with formal screening, the following boundary stages are now formally separated:

1. **Retrieved / Imported (`retrieved`)**:
   - Recorded in `import_history` and `project_publications`.
   - Linked via `import_id`.
2. **Pre-Screening Corpus Review (`retained` vs `removed`)**:
   - `retained`: Default state; candidate for formal screening.
   - `removed`: Manually removed during pre-screening review with a recorded decision in `pre_screening_decisions`.
3. **Formal Screening Admission (`admitted to Screening`)**:
   - `ScreeningInputService` and `get_active_publications` strictly query records where `pre_screening_status = 'retained'` (or `IS NULL` for legacy fallback).
   - Pre-screening removed records are excluded from screening input candidate sets and duplicate groups.
4. **Formal Screening Stage (`screened`, `included`, `excluded`)**:
   - Recorded in `screening_decisions` table with explicit outcomes (`include`, `exclude`, `maybe`).
   - Counts towards PRISMA `records_screened_title_abstract` and `records_excluded_title_abstract`.

## 3. Data-Model Changes

### Migration 0030: `migrations/0030_pre_screening_imported_records.sql`
- Added columns to `project_publications`:
  - `import_id TEXT DEFAULT NULL`: References the import/retrieval execution.
  - `pre_screening_status TEXT NOT NULL DEFAULT 'retained'`: Tracks review status (`retained` or `removed`).
- Added performance indices:
  - `idx_project_publications_import` on `(project_id, import_id)`.
  - `idx_project_publications_pre_screen` on `(project_id, pre_screening_status)`.
- Added `pre_screening_decisions` audit table:
  ```sql
  CREATE TABLE IF NOT EXISTS pre_screening_decisions (
      decision_id TEXT PRIMARY KEY,
      project_id TEXT NOT NULL REFERENCES projects(project_id) ON DELETE CASCADE,
      record_id TEXT NOT NULL,
      import_id TEXT,
      status TEXT NOT NULL,
      reason TEXT,
      notes TEXT,
      reviewer_id TEXT NOT NULL,
      decided_at TEXT NOT NULL,
      created_at TEXT NOT NULL
  );
  ```

### Domain Models (`app/domain/pre_screening.py`)
- `PreScreeningStatus`: Enum (`retained`, `removed`).
- `PreScreeningRemovalReason`: Controlled enum (`clearly_outside_scope`, `retrieval_artefact`, `incomplete_record`, `other`).
- `PreScreeningDecision`: Pydantic domain entity validating:
  - Removal decisions require a non-null `reason`.
  - If `reason == 'other'`, `notes` cannot be blank.

## 4. API Changes

### Endpoints (`app/api/routers/pre_screening.py`)
1. **`GET /api/v1/projects/{project_id}/imports/{import_id}/records`**
   - Query parameters: `search` (string), `status_filter` (`retained`, `removed`, `all`), `offset` (int), `limit` (int, default 50, max 500).
   - Returns `ImportedRecordsPageResponse` with total, pagination offsets, persisted counts summary (`total_imported`, `retained_count`, `removed_count`), and list of `ImportedRecordResponse` items.
2. **`POST /api/v1/projects/{project_id}/imports/{import_id}/records/{record_id}/remove`**
   - Body: `PreScreeningRemovalRequest` (`reason`, `notes`, `reviewer_id`).
   - Updates status to `removed` and creates an audit decision row.
3. **`POST /api/v1/projects/{project_id}/imports/{import_id}/records/{record_id}/restore`**
   - Body: `PreScreeningRestoreRequest` (`reviewer_id`).
   - Updates status back to `retained` and records restore decision.

## 6. PRISMA Accounting Behavior

### Invariants Verified
- **Invariant 1**: Pre-screening manual removal is strictly distinct from formal Screening exclusion.
- **Invariant 2**: Pre-screening removed records are excluded from `ScreeningInputService` and `get_active_publications`, ensuring they **never enter Title/Abstract screening**.
- **Invariant 3**: `records_screened_title_abstract` and `records_screened_full_text` are **not inflated** by pre-screening removals.
- **Invariant 4**: PRISMA metrics expose `records_removed_prescreening` as a separate, authoritative count derived directly from SQLite state.

## 7. Migration & Backward Compatibility

- SQLite migrations run non-destructively with `DEFAULT NULL` and `DEFAULT 'retained'`.
- Legacy imports where `import_id` was `NULL` are dynamically linked upon first review lookup (`_ensure_import_linked_with_conn`) using source format or provider name matching `import_history`.
- No historical records are altered or lost.

## 9. Known Limitations

- Single-record removal and restoration: Current implementation operates per record. Multi-select batch removal may be added as an enhancement in a subsequent slice.
- Search indexing: Uses SQL `LIKE` queries bounded by page limits; suitable for retrievals up to 50,000 records without external search engines.
