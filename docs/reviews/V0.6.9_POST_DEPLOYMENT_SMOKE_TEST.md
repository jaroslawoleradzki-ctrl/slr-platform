# SLR Platform v0.6.9 Post-Deployment Smoke Test

Post-deployment smoke-test record for SLR Platform v0.6.9.
Documentation/diagnosis only. No application code was modified,
no production state was changed, and no release or tag action was performed.

## Deployment state

- SLR Platform v0.6.9 deployed to production.
- Application starts and UI is accessible.
- This report records manually observed production behavior only.

## Manual production test

- Manual production smoke test was performed against the deployed v0.6.9 instance.
- Scope: application accessibility, Crossref Fetch All, and manual Resume.
- No automated production test suite was executed as part of this observation.

## Crossref Fetch All

- Crossref Fetch All executes using the new v0.6.9 bounded planner.
- Production UI reported:
  - 6 deterministic physical queries
  - partial execution
- Fetch All reached 5000 records.
- Resume was manually triggered after the partial stop.

## Resume test

- Resume was manually triggered from production.
- Resume endpoint returned successfully.
- No HTTP 500 was observed.
- No traceback was observed.
- No `IncompatibleCrossrefPlanError` was observed.
- Crossref continued to return publication data after Resume.

## Provider/API evidence

- The execution API reported:

  - provider: `crossref`
  - message:
    `"Fetch-all stopped early (partial): Stopped by the fetch-all safety limit
    before the provider reported its final page."`

- Therefore the observed partial status was caused by the application's
  fetch-all safety limit, not by Crossref failing to respond.

## Safety-limit observation

- The partial execution status corresponds to the application's fetch-all
  safety limit being reached at 5000 records.
- The provider was still returning publication data.
- There is no evidence that Crossref failed to respond or terminated the stream.

## UI observation

- The frontend nevertheless displayed:

  `"Część providerów nie odpowiedziała: crossref"`

- This message is semantically inaccurate for the observed case: Crossref did
  respond and continued to return data; execution stopped because of the
  application-side safety limit.
- Recorded as a UX/semantic follow-up, not as a v0.6.9 release blocker.

## Errors observed

- HTTP 500: none observed.
- Traceback: none observed.
- `IncompatibleCrossrefPlanError`: none observed.
- Crossref provider failure: none observed.
- Backend regression: none observed.

## Release assessment

- v0.6.9 planner behavior was observed in production as expected:
  bounded planning, deterministic physical queries, successful Resume request,
  continued Crossref data delivery.
- The safety-limit partial stop is expected application behavior.
- The misleading frontend provider message does not block the v0.6.9 release.
- V0.6.9 deployment is verified by this smoke test.

## Follow-up candidates

- UX/semantic follow-up: distinguish "stopped by application safety limit"
  from "provider did not respond" in the frontend Fetch All status/message.
  - When the backend reports a safety-limit partial stop with the provider
    still responding, the UI should not report the provider as non-responsive.
  - Backend message already carries the correct cause; only the frontend
    presentation needs review.
  - Not a v0.6.9 release blocker.
- No backend, planner, Resume-contract, or release follow-up is indicated
  by these observations.
