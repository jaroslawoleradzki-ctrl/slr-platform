## Existing Screening boundary

The baseline has no persisted corpus-finalization event and no persisted screening-membership table.

The current boundary is derived in `ScreeningInputService.get_input_set()`:

1. Read all project publications.
2. Require all duplicate groups to have review decisions.
3. Require approved duplicate groups to have technical merge records.
4. Read active, non-superseded publications.
5. Return those active publications as the `ScreeningInput`.

`TitleAbstractScreeningService` then reads this live input on overview/list/get/decision operations. The first saved title/abstract decision is the first persisted formal screening activity for a record. There is no explicit user operation that freezes or admits a corpus before this happens.

Therefore:

1. A retrieved/imported record currently becomes eligible for Screening when the live duplicate-readiness checks pass and it remains active.
2. The transition is implicit and derived, not explicitly initiated by a finalization action.
3. The baseline has no equivalent of prepared corpus, finalized corpus, or admitted-to-Screening state.
4. Additional imports can change the live Screening input after screening has begun.
5. There is no admission operation, so there is no admission idempotency guard. A record can appear in the live input again after a later import if it remains active.
6. Retrieval/import is represented by `import_history` and `project_publications`; duplicate state is represented by duplicate review decisions, merge records, and `superseded_by`; formal decisions are append-only rows in `screening_decisions`. There is no separate screened, admitted, or pre-screening-removed state.

## Existing PRISMA accounting

`PrismaMetricsService` currently derives:

- `records_identified_providers` and `records_identified_imports` from successful or warning `import_history` rows, summing their reported `records_count`.
- `total_identified` as the sum of those two import-history categories.
- `records_after_normalization` and `records_before_dedup` from the current Working Collection count.
- `records_after_technical_merger` from the current active publication count.
- `records_screened_title_abstract` and `records_screened_full_text` from workflow status evaluated counts.
- stage exclusions from workflow status final outcomes.
- synthesis eligibility from the current quality-assessment workflow.

The current PRISMA model has no pre-screening-removal field and no finalization snapshot. It therefore cannot currently prove that a removed-before-screening record was excluded from `records_screened`; the required state does not exist yet. WP4 does not alter these calculations because doing so without WP1's disposition contract would create an incompatible interpretation.

## Corpus lifecycle

The required lifecycle is:

`retrieved/imported → prepared corpus → finalized for Screening → formal Screening → PRISMA decisions`

The WP4 contract added in `app/domain/corpus_finalization.py` names the two dispositions that cross the WP1/WP4 boundary:

- `retained_for_screening`
- `removed_during_pre_screening`

It also requires a removal reason for the second disposition and preserves canonical record IDs and provenance references.

## Finalization semantics

The baseline is missing the domain state required to safely implement finalization. WP4 therefore does not add a competing persistence model or expose a premature endpoint/UI action.

The eventual operation must atomically:

1. read the prepared disposition set;
2. capture source, duplicate, pre-screening removal, and retained counts;
3. persist one immutable finalization event and its member snapshot;
4. admit retained IDs exactly once to the formal Screening corpus;
5. return the existing event on retry rather than creating another admission.

The safe product decision still required after WP1 integration is that finalization is immutable. New imports after finalization must remain pending for a new explicit corpus event; they must not silently change historical Screening membership. Reopening or appending requires a separately named product operation and audit event.

## Data model

No database tables were added in this branch because the required pre-screening state is owned by WP1 and is not present at the baseline.

The minimum future persisted model is:

- `corpus_finalizations`: project, event ID, created timestamp, source count, duplicate count, pre-screening removal count, retained count, and provenance summary.
- `corpus_finalization_members`: event ID, canonical record ID, disposition, admission status, and removal provenance/reason where applicable.
- a uniqueness rule preventing two admissions of the same project/event/record and a project-level state rule preventing an implicit post-finalization append.

These are integration requirements, not an implementation of WP1's storage schema.

## API

No finalization endpoint was added. The current API exposes screening operations and PRISMA metrics, but no corpus boundary operation. Adding an endpoint before the WP1 contract exists would require guessing how pre-screening removal is stored and would risk allowing the live publication collection to bypass finalization.

The future API should provide a read-only preparation summary and an explicit `POST` finalization operation. The POST must return the event ID, immutable counts, and admitted record IDs or a stable member summary. A repeated request must return the same event and counts.

## UI

No finalization action was added to the current Screening page. That page currently starts from the live `ScreeningInput` and has no safe source for a pre-screening-removed count.

After WP1 supplies the contract, the UI should show:

`Imported/retrieved: N` · `Removed before Screening: N` · `Ready for Screening: N`

and require confirmation with wording equivalent to “Przekaż do screeningu”, explicitly stating that retained records become the formal Screening population. A finalized state must replace the action and prevent accidental retries.

## Audit trail

The baseline has import history and append-only screening decisions, but no corpus event that connects a precise prepared set to Screening. The future event must preserve project, event timestamp, source/import provenance summary, counts, and member IDs. User attribution should use the application's existing identity/audit mechanism if one is available at integration time; WP4 does not invent an account identity.

## Idempotency

The current live-input architecture has no finalization operation to retry. The contract requires the future event to be keyed by project and finalized corpus identity, with a unique admission constraint. Finalizing once, reloading, and retrying must return the existing immutable event without inserting new members.

## Duplicate handling

The baseline's technical duplicate handling is upstream of Screening: duplicate review decisions and merge records determine active canonical publications. WP4 does not change DOI normalization, provider retrieval, duplicate grouping, or merge behavior. A future finalization snapshot must capture canonical record IDs after that existing readiness boundary and retain source provenance for each member. The same DOI from multiple import paths must resolve through existing canonicalization before admission; it must never create two Screening members for one canonical record.

## Additional imports after finalization

The baseline currently permits imports to alter the live input after screening starts. This is a reproducibility defect addressed by the required future state transition. After a finalization event, later imports must remain pending until an explicit new finalization event is created. They must not mutate the historical event or silently enter its Screening population.

## Legacy-project compatibility

Existing projects may already have screening decisions without a finalization event. WP4 must not fabricate a historical timestamp or pretend that an inferred event occurred. The integration should expose an explicit deterministic legacy state, for example `legacy_screening_without_finalization`, based on the presence of screening decisions and absence of a finalization event. Such projects need a deliberate migration/product decision before new finalization semantics are enforced.

## PRISMA invariants

The accounting primitive added in `app/domain/corpus_finalization.py` enforces:

`source_records = duplicates_removed + pre_screening_removed + retained_for_screening`

and counts `retained_for_screening` independently from `pre_screening_removed`. The intended formal invariant is:

`records_screened <= records_admitted_to_screening`

and pre-screening removal must not increment `records_screened` or any formal Screening exclusion count. A record can contribute to `records_screened` only after it is in the persisted admitted member set and formal Screening semantics count it as screened.

The baseline cannot prove the second invariant because it has no admitted member set. This is explicitly WAITING_FOR_WP1/integration rather than silently inferred from the live Working Collection.

## WP1 integration contract

WP1 must provide a repository/service boundary that returns, for each prepared canonical record:

- canonical `record_id`;
- disposition: retained for Screening or removed during pre-screening;
- source/import provenance references sufficient for audit reconstruction;
- a removal reason or removal provenance for pre-screening removals;
- stable preparation/review state suitable for an atomic finalization read.

WP4 does not require or prescribe WP1 table names, status enums, reviewer workflow, or frontend state. The `PreparedCorpusProvider` protocol and `PreparedCorpusRecord` value object are the minimum semantic contract. WP1 should adapt its own schema to that interface.
