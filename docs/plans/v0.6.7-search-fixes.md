# SLR Platform v0.6.7 — Search Correctness Plan

## Scope

v0.6.7 obejmuje poprawki dotyczące:
- canonical Boolean semantics,
- provider translation,
- Crossref candidate retrieval,
- canonical validation,
- metadata enrichment,
- Semantic Scholar lossless/lossy classification,
- lifecycle search_run_audits.

Nie obejmuje zmian UI wydanych jako v0.6.6.

---

## Architecture and Pipeline Overview

Docelowy pipeline przetwarzania w `SearchEngine` oraz `FetchAllSearchService`:

```text
1. Candidate Retrieval (OpenAlex, Crossref, Semantic Scholar)
2. Normalization (Unicode, DOI, fields)
3. Initial DOI Deduplication across already-retrieved candidates
4. Metadata Enrichment:
   a. Reuse existing merged data (e.g. OpenAlex abstract for Crossref record with same DOI)
   b. If abstract is missing and DOI is present, perform external DOI lookup (OpenAlex -> Semantic Scholar)
   c. Preserve field-level & record-level provenance (discovered_by vs enrichment_source)
5. Local Canonical Validation (MATCH / NON_MATCH / INDETERMINATE)
6. Strategy Metadata Constraints (year, types, open access, etc.)
7. Persistence, Snapshots & Search Run Audit (with distinct counters)
8. User-directed Screening Import
```

## Work Packages

### WP1 — Crossref metadata enrichment (H-1 HIGH)

### Problem
Crossref w większości przypadków nie dostarcza streszczeń (w testach live 0% w próbie). W rezultacie rekordy kandydatów Crossref, których tytuł nie zawiera wszystkich wymaganych bloków canonical query (np. LEAN AND ENERGY AND CONTEXT), otrzymują status `INDETERMINATE`. Status ten jest zachowywany w celu ochrony recallu, co prowadzi do masowego przenikania niezweryfikowanych publikacji do screeningu i dramatycznego wzrostu nakładu pracy (precision degradation).

### Root cause
Brak warstwy wzbogacania metadanych (Metadata Enrichment) przed ewaluacją przez `CanonicalQueryValidator`. Jeśli publikacja nie posiada abstraktu w Crossref, walidator nie może rozstrzygnąć dopasowania i zwraca `INDETERMINATE`.

### Design
1. **Dwuetapowe wzbogacanie**:
   - **Krok A (Internal Merge Reuse)**: Po pobraniu wyników od wszystkich providerów i deduplikacji po DOI, jeśli ten sam DOI został pobrany np. z OpenAlex (z abstraktem) i Crossref (bez abstraktu), abstrakt zostaje natychmiast uzupełniony bez żadnego zewnętrznego wywołania sieciowego.
   - **Krok B (External DOI Lookup)**: Dla rekordów z DOI nadal pozbawionych abstraktu, system wykonuje bezpieczny, kontrolowany lookup po DOI (OpenAlex `https://api.openalex.org/works/https://doi.org/...` lub Semantic Scholar `https://api.semanticscholar.org/graph/v1/paper/DOI:...`).
2. **Provenance Distinction**:
   - `discovered_by`: Pierwotny provider (np. `crossref`).
   - `enrichment_sources` / `abstract_source`: Źródło wzbogacenia abstraktu (np. `openalex`).
   - Zachowanie `ProvenanceEntry` dla audytowalności.
3. **Safety Limits**:
   - Concurrency limit (np. semafor max 5 równoległych zapytań).
   - Rate limit handling (wykorzystanie istniejących mechanizmów klientów z `Retry-After` i pacingiem).
   - Maksymalny limit zapytań enrichment na job/run (np. 100 zapytań na provider).
   - Brak lookupu dla rekordów bez DOI lub jeśli abstrakt jest już obecny.
4. **Enrichment Failure Handling**:
   - Jeśli lookup zakończy się błędem (404, 429, timeout, brak abstraktu) -> rekord pozostaje z `abstract=None` i otrzymuje `INDETERMINATE` w canonical validation (recall jest chroniony).
5. **Liczniki i metryki**:
   - `enrichment_attempted`
   - `enrichment_succeeded`
   - `enrichment_failed`
   - `canonical_accepted_count` (MATCH)
   - `canonical_rejected_count` (NON_MATCH)
   - `canonical_indeterminate_count` (INDETERMINATE)
   - `deduplicated_count`

### WP2 — Semantic Scholar lossless classification (M-1 MEDIUM)

### Problem
`SemanticScholarQueryRenderer.render()` ustawia `is_lossless = not warnings`. Ostrzeżenia były dodawane tylko dla pól innych niż `SearchField.ANY`. Funkcja `_to_plain_text` usuwa jednak interpunkcję (np. myślniki `Energy-Efficiency` -> `Energy Efficiency`, nawiasy), co zmienia fizyczne zapytanie względem zapytania kanonicznego, a mimo to `is_lossless` wynosiło `True`.

### Root cause
Brak walidacji w rendererze sprawdzającej, czy `_to_plain_text` dokonało modyfikacji zawartości termów (usunięcie znaków interpunkcyjnych, myślników itp.).

### Design
1. W `SemanticScholarQueryRenderer.render()`:
   - Podczas renderowania każdego `SearchTerm` sprawdzić, czy `_to_plain_text(term.value) != term.value.strip()`.
   - Jeśli wykryto usunięcie lub zamianę znaków (np. myślników, nawiasów), dodać jawne ostrzeżenie: `"Semantic Scholar bulk query normalized punctuation/hyphens in term '{term.value}' to plain words; query may not match exact hyphenation/punctuation."`
   - Ostrzeżenie automatycznie ustawi `is_lossless = False`.
2. Sprawdzić również zachowanie dla `exact_phrase`, operatorów Boolean (`AND`/`OR`/`NOT`) oraz zagnieżdżonych grup.

### Files likely affected
- `app/rendering/semantic_scholar.py`
- `tests/unit/rendering/test_semantic_scholar_renderer.py`
- `tests/unit/services/test_search_canonical_regression.py`

### Tests
- [x] Test: `SearchTerm(value="Energy-Efficiency")` -> `is_lossless is False` + warning.
- [x] Test: `SearchTerm(value="micro-CHP")` -> `is_lossless is False` + warning.
- [x] Test: `SearchTerm(value="Lean Management")` (bez interpunkcji) -> `is_lossless is True` (dla `SearchField.ANY`).
- [x] Test: Canonical regression query (wszystkie termy czyste) -> `is_lossless is True`.

### Acceptance criteria
- [x] Każda normalizacja termu zmieniająca znaki generuje warning i ustawia `is_lossless = False`.
- [x] Czyste zapytania Boolean bez interpunkcji pozostają `is_lossless = True`.

### WP3 — search_run_audits lifecycle (M-2 MEDIUM)

### Problem
Wiersze w tabeli `search_run_audits` nie posiadają klucza obcego `ON DELETE CASCADE` do tabeli `projects` i nie są usuwane w metodzie `delete_for_project` w repozytorium snapshotów / projektów, co prowadzi do powstawania osieroconych rekordów audytu po usunięciu projektu.

### Root cause
Migracja `0028_search_run_audits.sql` utworzyła tabelę z `project_id TEXT NOT NULL` bez powiązania FK `REFERENCES projects(project_id) ON DELETE CASCADE`, a `SqliteSearchResultSnapshotRepository.delete_for_project` usuwało tylko `search_result_snapshots`.

### Design
1. Zaktualizować `SqliteSearchResultSnapshotRepository.delete_for_project`:
   - Dodać `DELETE FROM search_run_audits WHERE project_id = ?`.
2. Zaktualizować `migrations/0028_search_run_audits.sql`:
   - Dodać `REFERENCES projects(project_id) ON DELETE CASCADE` (zgodnie z konwencją SQLite w pozostałych migracjach projektu).
3. Zweryfikować serwis usuwania projektów / kaskadę.

### Files likely affected
- `migrations/0028_search_run_audits.sql`
- `app/repositories/search_result_snapshot_repository.py`
- `tests/unit/repositories/test_search_result_snapshot_repository.py`

### Tests
- [x] Test: Utworzenie snapshotu i audytu dla `project_id`, wywołanie `delete_for_project(project_id)` -> usunięcie obu rekordów.
- [x] Test: Izolacja projektów — usunięcie projektu A nie usuwa audytów projektu B.
